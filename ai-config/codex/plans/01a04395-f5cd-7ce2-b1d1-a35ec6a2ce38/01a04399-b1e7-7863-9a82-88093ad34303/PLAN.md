# 投資判断中心へのアプリ再編計画 — 第1段階「企業ページ」

## Summary

- 現行HEAD・正本文書・実画面を照合した結果、必要なデータは存在しますが、25個のサイドバー入口、63 route、企業ページ最大100タブに分散し、「なぜ見るか・仮説にどう効くか・次に何をするか」が途切れています。
- 機関投資家の情報量を模倣するのではなく、証拠・反証・時点・鮮度・欠損を機関水準で管理しつつ、少数企業を深く理解する個人投資家の強みを前面に出します。
- 会社ごとにDiscoveryからReviewまで一つの「投資ケース」を持たせます。最初は企業ページだけを変更し、TodayのDashboard／朝会／実行は今回変更しません。
- Matt Pocockのdomain-modeling／codebase-designを適用し、曖昧な「確信度」を、データ品質・仮説解像度・影響確信度・判断利用可否・ユーザー判断へ分離します。

## 実装前の解釈エコー

- 変更前: 「変化」の利益増減ウォーターフォールなど、用途が不明なデータ表示と、多層のworkspace・preset・recent・詳細タブを利用者が自力で結び付ける状態。
- 変更後: 企業ページの初期画面で「なぜ監視・保有するか、何が変わったか、何が反証か、次に何をいつ確認するか」を一続きで確認し、必要な元データだけ同じ文脈から掘れる状態。
- 触るもの: 企業ページの情報設計・route、集約BFF契約、Desktop型・API client、関連テスト、worklogと変更決定記録。
- 触らないもの: Today、元データの収集・保存、DB schema、外部API、発注、Scheduler、ショートカット、Desktop配布。
- 完了条件: 開発版の実データ画面とfixtureで受入条件を証明し、exact-head Ready gateを通す。配布版反映は別途明示承認を得る。

## Implementation Changes

### 1. 企業ページを一つの投資ケースに再編

- 初期画面には次を判断順で表示します。
  - 現在の段階、主戦略、監視／保有状態
  - 投資仮説と「市場評価と事業実態の差」
  - 前回判断から変わった重要事実
  - 支持材料・反証材料・不足情報
  - Hard／Soft invalidation、T-stop
  - 次のKPI、イベント、確認期限、レビュー日
  - 保有中ならサイズ・PF影響・現在の継続／縮小判断
  - 出典、基準時点、公開・取得時刻、鮮度、利用可否
- 自動生成された単一の買い／売り評価や総合confidenceを主判断として表示しません。保存されたユーザー判断がなければ「未設定」とし、推測で補いません。
- 現在の「変化」画面とウォーターフォール類はUIから外します。計算処理・API・保存データは削除せず、将来の文脈付き再利用とrollbackを可能にします。
- 7 workspace、preset、recent chips、最大100タブの常設選択UIを廃止します。詳細は「事業・KPI」「決算・財務」「市場・需給」「証拠・履歴」の4文脈からのみ開けるようにします。
- 各情報は、判断段階・仮説への役割・意味・証拠・鮮度・次アクションを説明できる場合だけ主画面へ載せます。raw値、用途不明のスコア、投資判断を止めていない運用情報は載せません。
- `不明`、`中立`、`変化なし`と、`正式利用可`、`参考`、`未検証`を別状態として扱います。

### 2. API・route契約

- 読み取り専用の企業投資ケース集約契約を追加します。既存の仮説、watchlist、position、決算、財務、証拠、イベントを集約し、新しいDB書き込みやDDLは追加しません。
- 応答は、段階・戦略・仮説・市場とのギャップ・変化・支持／反証／欠損・否定条件・次KPI／イベント・保有文脈・判断利用可否・品質メタデータを明示します。
- 証拠項目にはsource tier、原典／locator、`as_of`、公開・取得時刻、freshness、判断上の役割を含めます。部分欠損はセクション単位で表示し、ページ全体を失敗させません。
- 企業リンクには `focus=case|business|earnings|market|evidence` の文脈を渡します。決算からは決算、保有からは投資ケース、市場統計からは市場の文脈へ着地させます。
- 既存の `?tab=` bookmarkは互換mappingを残します。`tab=changes`は投資ケースへ移し、存在しないtabや最後に見た無関係なtabへ黙って着地させません。
- 既存の財務集約、仮説・tranche・journal等の書き込み契約は維持し、「判断を更新」は既存の判断記録フローへ接続します。

### 3. 全体改善の後続順序

企業ページを実画面で確認した後、機能群ごとに監査結果と解釈エコーを提示して承認を得ます。

1. Earnings／Holdings: 決算変化・持ち越し・保有理由・出口条件を同じ企業投資ケースへ接続し、FundamentalsやAction Queueとの重複を整理。
2. Macro／Flow: 詳細データの正本画面は残し、企業KPI・決算・仮説へ影響する解釈だけを企業ページへ接続。単独の売買シグナルにはしない。
3. ナビゲーション: 候補発見→企業判断→決算→保有判断→記録の導線に再編し、互換routeは維持。
4. Today: ODR-0013との関係を別途判断し、明示承認があるまで3モードと内容を変更しない。

監査結果は各worklog内で「主画面に残す／統合する／文脈付き詳細へ下げる／非表示」の4区分にします。新しい恒久台帳・hook・検査制度は追加しません。

## Test Plan

- BFF契約テスト: 正常、部分欠損、stale、一次証拠なし、未保有、保有中、判断未設定を確認。
- Desktop focused test:
  - 初期画面の判断順と状態語彙
  - `decision_eligible=false`時の正式判断制限
  - 文脈付き企業リンク
  - legacy `?tab=` mapping
  - 「変化」画面とグローバルtab群が表示されないこと
- Visual QA: 1440×900と375×812で、保有・監視・欠損の各fixtureを確認。横スクロール、長大なカード壁、keyboard focusも確認。
- 実データQA: 既存BFF／PostgreSQLをread-onlyで参照し、現在確認した6326を含む代表企業で、出典・鮮度・欠損・遷移先を確認。
- 受入条件:
  - 最初の画面で投資理由、最大の変化または反証、次の確認事項が分かる。
  - すべての主表示が「何の判断に使う情報か」を説明できる。
  - 決算・保有・市場から企業へ1回の遷移で該当文脈へ着地する。
  - 元データへの詳細到達性を保ちながら、用途不明のrawデータを主画面へ出さない。
  - Todayに意図しない差分がない。
- focused検証後、worklogを固定してexact-head Ready gateを1回実行し、実画面証拠と同じSHAでpublish／mergeします。

## Assumptions and Approval Boundary

- 元データ・API・計算処理は維持し、今回は表示と集約契約を改善します。
- 企業ページ以外は監査対象には含めますが、変更は機能群ごとの承認後に行います。
- main checkoutでは編集せず、承認後に専用worktreeとFull worklogを作成します。
- この解釈エコーへの「はい」を実装開始の承認とし、Desktop配布は別の明示承認事項とします。

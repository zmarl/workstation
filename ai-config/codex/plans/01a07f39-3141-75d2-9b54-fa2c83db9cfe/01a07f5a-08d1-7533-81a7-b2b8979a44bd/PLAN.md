# 古いハーネス制約を整理し、現在の方針に揃える

## 目的と現在地

最初の改善単位は、**個人設定も含めた古い禁止・指示の整理**とする。Qwenの分析・通知は別プロジェクトの担当として対象外にする。:codex-annotation{index="1"}

9/7には制約の縮小が進んだが、変更がリポジトリ内に留まり、個人設定や関連手順に旧方針が残っている。実際にルール評価器で確認すると、ローカルビルドは今も`forbidden`になる。ビルド自体は実行していない。

製品側は、macro索引の修復時の成功証拠を確認できた。一方、朝スクリーニングは必要な列の欠落で失敗し、夜間回帰は中断ログがあり完了未確認。この復旧は次の改善単位として分離する。

## 変更内容

| 対象 | 変更前 → 変更後 |
|---|---|
| 個人のビルド禁止 | ローカルビルドを外部配布扱いする11本の禁止 → 削除。公開・配布・実通知などの禁止は維持 |
| Git操作の説明 | 「全工程が承認不要」という古いコメント → 現在の依頼・承認された作業範囲に従う説明 |
| 凍結中の作業案内 | 従来の無人修復・並行開発手順が混在 → 10/7までの凍結方針と通常手順を区別。順番待ちを理由に自動修復を再開しない |
| レビューの報告制限 | 「不足テストは1件だけ」 → 件数で隠さず、異なる受入条件の不足を根拠・影響付きで報告。重複・好みの改善提案は増やさない |
| モデルの説明 | Sol・xhighなどの古いコメント → 設定値と利用者による選択を参照する説明 |

レビュー制限は、プロジェクトと個人のCodex設定、およびClaudeの通常・専門レビュー役の計6ファイルを揃える。

**モデル・推論強度・役名・エージェント上限は変更しない。** 旧モデル名を理由に親の選択を拒否する現行ゲートは確認できなかった。Claudeのコマンド権限、絶対パス実行禁止、`git clean`禁止も今回は緩和しない。

個人ルールの変更は他プロジェクトにも作用する。この影響を含めた整理を今回の計画に含める。ルールの合成では厳しい禁止が優先されるため、プロジェクト側の許可追加では代替しない。[Codex公式仕様](https://learn.chatgpt.com/docs/agent-configuration/rules)

## 実装・検証方法

- 専用worktreeで既存ファイルを限定編集する。判断理由は既存の凍結決定記録と1本のworklogへ残し、新しいゲート・台帳・常設検査は作らない。
- 個人設定は変更対象を事前保存し、変更直前にも他作業による更新がないことを確認する。個人設定の全文や秘密情報をリポジトリへ入れない。
- ルール評価器で、対象11形式のローカルビルドが旧禁止に一致しなくなることを確認する。公開・破壊・実通知などの代表例は、実行せず評価だけで禁止の維持を確認する。
- 設定ファイルの構文と生成されたSkill案内の整合を確認する。レビュー指示は「独立した不足が2件ある例」と「同じ不足を重複説明した例」で、重要な指摘を欠落・水増ししないことを確認する。
- 権限制約を変更するため、独立レビューを1回実施する。リポジトリは同じ検証済みコミット、個人設定は対応する差分とハッシュを対象にする。
- 承認された実装時には、必要なReady検証と通常のPR統合まで進める。設定反映確認のために実行中の他タスクを終了しない。

API・DB・分析ロジック・Scheduler・通知処理の変更はない。今回の検証目的でアプリの再ビルドや全体テストを追加しない。

## 完了条件と次の課題

完了は、**設定ファイルの変更、ルール評価の成功、関連指示の一致、新しく開始したセッションへの反映確認**までとする。既存セッションへの反映が未確認なら、その点を残して報告する。

変更は既存ファイル15前後を目安とし、増加が必要になった場合も新機構の追加へ広げない。復元時は今回変更した部分だけを戻す。

次の改善単位では、朝スクリーニングの列欠落と夜間回帰の中断を個別に調べる。毎回「変更前の問題 → 取った対策 → 実際の結果 → 残る課題」で整理し、登録・実装・実運用成功を分けて報告する。

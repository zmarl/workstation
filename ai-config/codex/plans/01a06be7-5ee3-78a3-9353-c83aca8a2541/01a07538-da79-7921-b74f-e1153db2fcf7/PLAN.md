# 並行開発・テスト・トークン消費をまとめて改善する計画

## 1. 目指す開発の流れ

独立した作業は、実装から必要な検証まで並行して進む。小修正は、その変更が壊し得る挙動を短く確認する。長時間の検証中は機械が実行を続け、AIは結果が必要になったときに短い情報を読む。

現在の問題は、次の四つが重なっている。

| 問題 | 改善後 |
|---|---|
| 別作業の監査・復旧・片付けが統合の前提になる | その変更に必要な証拠と、実際の依存だけを待つ |
| 小修正でも広い検証を予約し、修正のたびに繰り返す | 対象を正しく選び、修正中は失敗箇所、完成時に必要範囲を確認する |
| 待機中の状態取得・ログ読取・考察が続く | 詳細ログは保存し、既存の待機機能から終了結果を受け取る |
| 安全策・抽象化・テストが追加され続ける | 受入条件を満たす最小変更を行い、重複する仕組みを置き換える |

品質は、投資判断・保存・権限・実際の利用経路の検証で守る。コードやテストの行数だけで判断しない。

## 2. LLMの行動とトークン消費を直す

### 指示の矛盾を解消する

- [AGENTS.md](D:/Dev/Investment/AGENTS.md)を共通方針とし、Skills・開発手順・個人共通指示に残る相反する要求を削除・修正する。同じルールを複数文書へ追記しない。
- 局所修正では、対象・期待結果・最小検証が分かれば実装へ進む。詳細計画、広域調査、独立レビューを毎回の儀式にしない。
- 新しい抽象化・設定・状態管理は、今回の要求を既存コードで満たせない場合に限る。既存の呼び出し元が一つだけのために汎用基盤を作らない。
- レビューは正確性、要求逸脱、安全境界、未証明の受入条件に集中する。任意の改善を完了条件へ追加しない。
- モデルと推論強度は維持する。削減対象は不要な呼出し、入力、出力、やり直しとする。

### 既存の実行ラッパーを標準入口にする

以前の出力削減では、成功時の表示が約5万文字から約6千文字へ減った一方、待機・再実行・全経路への適用は残っている。既存のログ保存機能を利用して、Python・DB・Desktop検証の出力を統一する。

- 通常出力は、結果、件数、所要時間、失敗箇所、ログ保存先に限定する。成功時は原則2,000文字以内。
- 失敗時は代表的な原因と失敗テストを最大8,000文字で返し、必要な箇所だけ追加で読む。終了コード、収集失敗、未実行、警告は保持する。
- 進捗文字列と定期heartbeatはログに残し、AIへ逐次送らない。要約のために別のLLMを呼ばない。
- 待機は既存の実行セッション・ジョブ待機を使う。ツールの制約で待機を繰り返す場合も、変化のないログの再読や周辺調査を挟まない。
- Codexの`tool_output_token_limit`は履歴への大量流入を抑える補助として、このプロジェクトで2,000を候補に動作確認する。これは総トークン消費の上限ではなく、ラッパーと待機動作の修正を主対策とする。[公式設定仕様](https://learn.chatgpt.com/docs/config-file/config-reference)

## 3. 小修正の検証と、全体テストの総量を減らす

### 検証範囲を実装と手順の両方で修正する

- 日常の修正は、該当するテストと直接影響する呼び出し経路から始める。失敗を直している間は、失敗テストと追加変更の影響範囲を確認する。
- 完成時には、確定したコードで必要な検証を一度そろえる。全領域を選ぶのは、共通設定・保存契約など広い影響を具体的に説明できる変更に限る。
- ファイル種類だけでDB・Desktopの追加範囲を要求する手順を削り、自動選択と重複させない。
- 最終検証後の報告追記だけでコードを更新し、再検証を発生させない。mainが進んだ場合は統合候補を更新し、その候補の必要範囲を検証する。異なるコードの成功結果を無条件に流用しない。

### 選択器の具体的な無駄と漏れを直す

[既存のテスト選択設定](D:/Dev/Investment/scripts/development_test_selection.yaml)と実行入口を修正する。

- テスト収集とmarker分類を一度行い、DBテストが0件ならDBジョブを予約しない。収集失敗・不明を0件と扱わない。
- 同じ条件の対象をまとめ、重複実行を除く。現在確認できた、財務テストの二重収集も解消する。
- 財務表示とハーネス状態表示について、ソースだけを変更しても正しい関連テストが選ばれるよう既存の対応表を補う。
- 同一実行内の重複走査は共有する。全リポジトリの新しい依存解析基盤や、異なるcommit間の検証キャッシュは初期実装に加えない。

### 全体監査そのものを軽くする

直近の成功監査は約74分で、そのうちDB検証が約46分。頻度変更だけで済ませない。

- 全体監査でも、分類ごとに繰り返しているテスト収集を一回へまとめる。収集結果・marker・対象コードの対応は検証する。
- DBの準備時間とテスト本体の時間を、成功時も既存ログへ残す。次の必要な全体監査で、重い対象を特定する。
- 読取・通常の保存確認は、既存のトランザクションとrollbackによる再利用方式へ移す。空DB、構造変更、実commit、複数接続が受入条件のテストは新しいDBで実行する。
- 最初の安全な置換例は、broker連携の「保存禁止でテーブルが変わらない」テスト。以後は実測した準備時間の大きい対象から、同じ保証を保てるものだけ置き換える。
- 同じ故障を複数層で重複検証するテストは、必要な実行経路を通るテストへ統合する。テストを別ファイルに分割しただけ、重いテストを週次へ移しただけでは総量削減と数えない。
- 全体監査は週次と、検証方式を変える一連の作業の最終版で実施する。表示・診断などの小修正ごとの自動全体監査は外す。

## 4. 作業間の不要な順番待ちをなくす

### 停止を、その作業に必要な範囲へ限定する

- 選択済みの方針に従い、別監査の未完了・読取不能・起動失敗だけでは、必要な検証が成功した無関係な変更を止めない。監査状態は「未確認」のまま表示する。
- その変更自身の検証不成立、確認済みの関連不具合、所有権・秘密情報・証拠の不整合は停止する。
- 各PRが同じ監査障害の修復ジョブを自動生成する経路を外す。共有障害の修復は既存の担当とジョブを使う。
- 検証成功とworktreeの片付けを分ける。必要な証拠が保存・検証済みで、実行資源が安全に解放された後の削除失敗は、片付け待ちとして扱う。
- 「別タスクが終わるまで」ではなく、必要なAPI契約・データ・変更箇所を依存条件として示す。契約が確定していれば、利用側の実装・単独検証を先に進め、実接続が必要な段階だけ待つ。

### 隔離済みDBとCPUを適切に並行利用する

- 既に実行ごとに隔離されているテストDBを利用し、まず通常検証用1枠と監査・旧worker用1枠に分ける。
- 旧workerが使う既存DB lockを維持し、対応済み通常検証だけ第2枠を使う。同一ジョブの二重実行は既存の実行lockで防ぐ。
- 同じDB内で表を消すテストやmigrationは直列のままとする。ホスト全体のworker数は増やさない。
- Python・Vitestの既定並列数を各実行2にし、既存設定が同期・非同期の子プロセスまで届くよう修正する。
- 切戻しは第2枠の新規受付を止め、実行中の処理は自然終了させる。起動済みworkerも受付時に設定を確認する。所有外プロセスの停止は行わない。

### 状態確認を軽くする

[状態確認コマンド](D:/Dev/Investment/scripts/dev/harness_status.py)の`--summary`は現在の状態を先に返し、期間集計は明示指定時だけ行う。待機の確認で全履歴を毎回読み直さない。対象ジョブだけを確認できる入口を既存コマンドに追加し、別の監視サービスは作らない。

## 5. 実施順と完了条件

実装は、次の三つのまとまりで進める。

1. **出力・待機・指示の統一**：DB復旧を待たずに改善できる。実行ラッパーの短い出力と、通常のLLMの使い方まで確認する。
2. **選択器とテスト総量の削減**：不要なDB予約、重複実行、対応漏れを修正し、既存DBテストを限定して軽量化する。
3. **停止条件と資源枠の修正**：無関係な監査から統合を切り離し、旧worker混在を含む2枠動作を確認する。

担当範囲が重ならない部分は並行して進める。同じ基盤修正のために作業・修復PRを次々に作り直さず、同じ作業IDと保存済み状態で継続する。

完了は、次の実行結果で判定する。

- DBを使わない小修正で、DB予約・コンテナ起動・全体テストが発生しない。
- 一つのテスト失敗を直す反復で、無関係な領域を再実行しない。
- 監査DBが実行中でも、独立した通常DB検証と非DB検証が進む。
- 別監査の欠損・失敗・片付け待ちが無関係な作業を止めず、当該変更の不正証拠や関連不具合は止まる。
- 成功・失敗・timeoutのいずれでも結果を取り違えず、AIへ返す出力量が規定内に収まる。通常のCodex・Claude経路で確認する。
- 代表的な競合検証を同じテスト集合で比較し、待ち時間と完了時間を測る。通常検証は既存目標の3分を目指し、重い検証は別に計測する。
- 必要な全体監査を最後まで完走させ、総時間・DB準備・本処理を比較する。短縮効果のない最適化は採用しない。
- 総トークン量を取得できる場合は既存セッション記録で比較する。取得できない場合は出力量とAIへの往復回数を示し、「総トークン削減を実証済み」とは報告しない。

今後も、追加テストは新しく守る挙動を明確にし、重複があれば置き換える。遅さは既存の時間記録で確認し、新しい常設ゲートや監視役は増やさない。

対象は開発ハーネスと、このリポジトリに効く指示・設定。アプリ機能の拡張、本番データの修復、Scheduler再登録、権限緩和は含めない。

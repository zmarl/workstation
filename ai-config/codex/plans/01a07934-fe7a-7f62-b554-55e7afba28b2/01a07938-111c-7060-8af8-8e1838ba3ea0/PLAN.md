# 初回決算分析の文書再編と、荏原の全数値表をアプリへ届ける実装計画

## 1. 目的と確認できた現在地

今回の成果物は、**内容を失わずに体系化した文書と、最初の実装を開始できる具体的な仕様**とする。現在仕様を本文で読み、原発言・訂正・比較案・失敗記録は全文履歴へ戻れる構成にする。

最初の実装成果は、選択いただいたとおり、**荏原の初回分析に必要な全数値表を原資料から計算し、既存アプリで根拠とともに確認できること**とする。

調査で確認した現在地は次のとおり。

| 対象 | 確認結果 |
|---|---|
| 営業利益モデル | [PR #352](https://github.com/zmarl/Investment/pull/352)は統合済み。「まだOpen」「mainは8月31日版」という貼付文の状態は更新が必要 |
| 財務計算 | mainにPL 5項目の純計算、原資料入力、Qwen・保存・画面への接続がある。新しいQwen向け計算観測は累計前年同期の5項目に限定 |
| アプリへの到達 | 9月7日未明の保存証拠に、7602のDB保存・BFF読戻し・通常画面確認がある。今回は実画面を再検証していない |

| 深掘り | 貼付資料に加え、5分類・87主決定・20具体化の記録を確認。別系列の決定と項目別に対応づける必要がある |
| 荏原の試験 | 手照合入力による表と実Qwen出力がある。共通計算への接続は当時未実施で、文章にも誤り・脱落が残る |

## 2. 文書をどう体系化するか

入口は既存のDocs Indexを維持し、そこから[初回分析の統合仕様](D:/Dev/Investment-qwen38-deep-analysis-discussion/docs/design/qwen38-earnings-initial-analysis-evaluation-map.md)と各専用仕様へ案内する。作業日時の順に読まなくても、全体を理解できる構成にする。

| 文書の役割 | 整理する内容 |
|---|---|
| 全体の入口 | 目的、取得から振り返りまでの流れ、責務分担、確認日付きの実現範囲、読む順序 |
| 初回分析の本文 | 入力条件、全社・全セグメント等の評価方法、理由、具体例、表示、欠損時の扱い、完成条件 |
| 計算の専用仕様 | 入力、式、単位、精度、比較可能性、例外、出典、保存・Qwen・画面への受渡し |
| Qwenの技術仕様 | 原文と計算結果の入力、分割処理、数値参照、原因と寄与の対応、全社評価、部分失敗 |
| 深掘りの本文 | 需要、利益構造、成長と持続性、資金、競争・期待の5目的で方法を整理。起動・保存方式は既存の専用仕様へ接続 |
| 運用手順 | 結果の開き方、数値・本文・根拠の確認、未読や失敗への対応、訂正・後着更新、次回決算との照合 |
| 決定・履歴・研究 | 原発言、推奨と別案、採否、理由、訂正、失敗した出力、未採用候補を保存 |

整理は次の順序で行う。

1. **対象資料を固定する。** 貼付資料、今回発見した目的別文書、直接関連する黒字化・条件試算の仕様を一覧化し、所在・版・未コミット差分を記録する。他担当の作業コピーは編集しない。
2. **内容の対応表を作る。** 元の章・決定番号から、新しい本文・専用仕様・全文履歴のどこへ残すかを対応づける。異なる会話の同番号を混同しない。
3. **現在の説明を更新する。** 採用状態、コードの実装範囲、実データの検証範囲、アプリ到達を別々に示す。古い失敗記録は当時の記録として保持する。
4. **重複する現在仕様を一本化する。** 初回の評価・表示契約は統合仕様へ集約する。旧Q別文書は全文を履歴として保存し、既存の参照箇所から後継へ案内する。
5. **運用から読める形へ仕上げる。** 未実装の手順にはその状態を明記する。Taskの進捗は既存の次アクション管理台帳へ接続し、別の進捗台帳を増やさない。

各分析項目は、**何を判断するためか → 必要な材料 → 方法・計算 → 読み方 → 反証・限界 → 不足時の扱い → 確認例**の順で説明する。固有の条件・理由・例外を、短い要約へ置き換えて失わない。

## 3. 最初の実装仕様：荏原の全数値表

対象は荏原製作所の2026年12月期2Qとする。最初は既存試験と比較できる公表日単位の再構成を用い、「当時アプリが取得済みだった情報の再現」と区別する。

| 順序 | 実装内容と利用者が確認する成果 |
|---|---|
| ① 原資料と比較条件 | 当期・比較資料、会社予想の各版、必要な注記を固定。原本、位置、期間、範囲、単位、精度、取得・公表時点を追える |
| ② 全数値表 | 累積PL・予想進捗、単体PL、全セグメント累積・単体と調整、受注・受注残、開示KPI、累積CF、BS、配当・株数の比較を生成 |
| ③ 共通結果の保存 | 表の値、計算式、入力参照、比較条件、不足理由を一つの計算結果として固定し、再読込みしても一致する |
| ④ アプリへの先行表示 | 既存銘柄画面で表・出典・計算不能理由を確認できる。「数値確認済み」と「Qwen文章分析未実施」を区別する |
| ⑤ 次の分析へ引渡し | 確認済みの同じ計算結果と原文を、後続のQwen改善へ渡せる |

実装方針は以下に固定する。

- [財務計算の専用仕様](D:/Dev/Investment/docs/design/financial-performance-compiler-spec.md)と既存純計算を拡張する。PL・残高・期間フロー・比率・一株値の適用条件を分け、Qwenや画面へ計算式を複製しない。
- 過去の手照合JSONは期待値の確認に使う。原資料からの入力処理を置き換える本番データとして埋め込まない。原本取得・抽出の不足は既存経路で原因を確認し、並行する取得修復と重複実装しない。
- 日本円の金額はDecimalで正規化する。原表記・原単位・精度を残し、表示は既存の合意済み表順と比較列を保つ。企業規模による新しい自動単位切替閾値は設けない。
- EPS、率、受注残、BS残高を累積差で単体化しない。CFはまず同期間の累積比較とする。比較不能でも当期実数を残す。
- 前年進捗の分母は前年当時の会社予想とする。発表前コンセンサスを確認できなければ、その理由を表示する。全数値表の完成を「全セルが数値で埋まること」と定義しない。
- 数値の先行保存は既存の管理された入力一式の保存機能を拡張する。未生成の文章をQwen分析済みとして保存しない。
- BFFは計算結果をQwen分析とは独立して取得できるようにし、既存の計算型を再利用する。旧保存分析との互換性を保ち、画面を開くGETで取得・計算・Qwen生成を起動しない。
- 数値確認後のQwen改善は次の実装単位とする。長期予測、PER逆算、モデル変更、高度分析13候補の実装は初回数値表の前提にしない。

## 4. 深掘りすべき内容と、その順序

最優先は、分析項目を増やすことより、既存の要求を具体例で判定できるようにすることである。

| 優先 | 詰める内容 | 決める成果 |
|---|---|---|
| 1 | 原因説明の十分さ | 会社説明・計算上の分解・仮説を区別し、原因、仕組み、相殺、不明をどこまで説明すれば役立つか |
| 2 | 利益と現金の接続 | CF改善を利益改善と同一視せず、債務・回収・在庫・投資の影響と残る負担を説明する例 |
| 3 | 予想と時間の対応 | 前年比・前回予想比、実績計上期、将来計上、織込み済み・未織込みを取り違えない例 |
| 4 | 全社評価と重要性 | 累積微増と単体減益、事業間の正負寄与、重要な財務・予想条件を同時に扱う例 |
| 5 | 深掘りへの引渡し | 何が分かれば評価が変わるか、必要な証拠、確認先、時期、反証条件、終了条件 |
| 後続 | 業態別・高度分析 | 共通方式で誤る業態から具体化し、追加モデルは必要データと比較評価が揃った候補から検討 |

未取得、未読、処理への未投入、モデルの脱落、開示内では不明、比較不能を分ける。全原因の確定やIR回答を初回保存の待ち条件にしない。

Qwen改善は、既決の「数値と比較条件を本文まで保持」「原因と寄与額の関係を検証」「全社評価へ元の数値と重要事項を直接渡す」の3点を順に実装する。

## 5. 検証と完了条件

**文書再編の完了条件**

- 対象として固定した全資料の固有論点・理由・訂正・制約に保存先がある。
- 現在仕様、採用理由、未採用候補、当時の実行結果を取り違えずに読める。
- 初回・計算・Qwen・深掘りの入力と出力がつながり、最初の実装対象と後続対象が明確。
- 旧参照から内容へ戻れ、内部リンク・メタデータ・対象文書の既存検査を通る。文書検査の成功だけで内容保持を証明したことにはしない。

**最初の実装に設定する受入条件**

- 原資料→入力検証→共通計算→保存→BFF→画面を通し、同じ値・版・根拠が保持される。
- 単位混在、赤字・ゼロ、EPS、セグメント組替え、予想版、丸め差、欠損・競合を確認する。
- 荏原の既知事例として、CFの前年／当年上期、配当の前年比／前回予想比、累積／単体の違い、全事業と調整の保持を確認する。会社開示値と算術合計の丸め差を強制的に消さない。
- 後着・訂正を加えても保存した旧版は変わらず、追加版として追跡できる。
- このPCの通常アプリで荏原の表と出典を開ける。検証用画面やビルド成功だけで完了にしない。
- Qwen改善時は過去の失敗例と未使用例を分け、生出力を保存して確認する。文章を手直しした見本をモデルの成功結果としない。

今回の再編では製品コード・共有DB・通知・Schedulerを変更しない。文書を完成させた後、上記の数値表実装を最初の開発単位として進められる状態にする。

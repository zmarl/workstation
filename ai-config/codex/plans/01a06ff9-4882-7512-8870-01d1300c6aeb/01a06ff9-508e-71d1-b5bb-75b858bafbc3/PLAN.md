# 並行開発を止める条件の限定と再開経路の改善

## 方針

**障害の影響を受ける作業だけを止め、無関係な開発と必要な復旧を進められる状態にする。** 既存の監査復旧担当とは重複せず、不足部分を補う。

確認できた問題は次の三つ。

- PowerShell本体を禁止するユーザー共通設定が、通常の読み取りまで拒否している。
- 共有監査の読み取り例外が、一律に全マージ停止へ変換される。
- DBの件数・最新月の不一致が別作業で記録されている。これは影響するデータ補完を止める理由として維持する。

現在は調査・計画段階で、設定変更や復旧は未実施。

## 1. PowerShellの誤停止を解消する

対象は [host-executables.rules](C:/Users/kazum/.codex/rules/host-executables.rules) と、必要な既存の禁止ルール。

- PowerShell実行ファイルを丸ごと禁止する2規則を、危険な呼び出しを対象とする規則へ置き換える。一括許可の規則は追加しない。
- エンコード実行、破壊的操作、公開、Scheduler登録などの既存境界を維持し、PowerShellの絶対パスによって禁止を回避できないようにする。
- 他の実行ファイルに対する規則は今回変更しない。
- 変更前の内容を保存し、適用直前に他作業による変更がないことを照合する。

ルールは複数ファイルを合わせて評価し、最も厳しい判定が優先されるため、許可規則の追加ではなく禁止範囲を修正する。[公式のルール仕様](https://developers.openai.com/codex/rules)

## 2. 共有監査の停止を必要範囲へ限定する

既存担当の監査記録・ワーカー・復旧処理の修正を先行依存とし、その統合後の不足だけを既存の停止判定へ反映する。

- 失敗した検証と対象変更の関係が確定できる場合は、その対象だけを停止する。
- 古い監査や別対象の記録は、現在の変更に適用されないことを確認できる場合だけ停止判定から除外する。
- 記録の破損で対象を特定できない場合は、無関係だと推測して通さない。停止理由に対象記録・原因・既存の復旧経路を残す。
- 修復自身は、既存の専用経路で必要な検証を満たせば統合できるようにする。監査記録の手動書換えや未検証の成功扱いは行わない。
- 新しいキュー、監視サービス、検査台帳は増やさない。

製品API・DBスキーマ・Desktop画面は変更しない。内部の診断情報は既存の状態表示・エラー出力へ追加し、共有キューの記録形式を増やさない。

## 3. 復旧後に作業を再開できる状態にする

- 既存の再開処理で、監査待ち・資源待ち・検証失敗・実行前の拒否を区別する。
- 同じ検証対象の有効な成功証拠を再利用し、重い監査を重複投入しない。mainや変更内容が変わった場合は必要な証拠を取り直す。
- DB異常は対象系列・依存作業・解除条件を既存台帳に接続する。DB修復や大量補完は既存担当に残す。
- 他作業のプロセス・作業コピー・ロックを停止せず、競合する操作だけを延期する。

## 検証と完了条件

- ルール評価で、通常の読み取りがPowerShell本体の禁止に該当せず、危険操作の禁止が維持される。危険操作は実行せず判定だけを検証する。
- 実際のCodexから、今回拒否された読み取りと監査状態確認が成功する。
- 既存テストで、無関係な変更は進み、影響する変更・対象不明の破損・不正な証拠は停止する。
- 監査待ちからの再開で、検証の二重投入や他作業への割込みが起きない。
- 既存修復の統合後、PR #388について共有監査の読み取り不能が解消したことを確認する。他担当PRのマージは引き取らない。

設定の読込みに再起動が必要な場合も、稼働中の他作業を中断しない。設定保存済みと実際の適用確認済みを区別し、適用確認まで完了扱いにしない。

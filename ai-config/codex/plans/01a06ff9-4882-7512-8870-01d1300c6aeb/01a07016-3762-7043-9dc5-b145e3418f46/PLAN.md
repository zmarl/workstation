# 並行開発の誤停止を解消し、障害から再開できる状態にする

## 1. 改訂方針

**Codex標準の安全審査を生かし、独自設定による誤停止と、共有監査の過剰な停止範囲を修正する。** 他タスクの中断や、禁止コマンドの回避を解決手段にしない。

前回の検証を訂正する。PowerShellを包んだ文字列への`execpolicy check`だけでは、実行時の判定を再現できない。公開実装にはPowerShellの中身を分解する経路があり、CLI検査との相違も報告されている。前回の「37ケース中6件不一致」を、そのまま実行時の保護欠落とは扱わない。[公開実装](https://github.com/openai/codex/blob/main/codex-rs/core/src/exec_policy.rs)・[相違の報告](https://github.com/openai/codex/issues/24201)

今回の対象は、共通ルールの限定修正、監査の停止判定・診断・再開処理の不足補完、DB異常の依存関係の記録。製品API・DBスキーマ・Desktop画面は変更しない。

## 2. コマンド実行の誤停止を直す

**先に判定経路を確認し、その後に設定を適用する。**

- Desktopが使う実行エンジンと、検証用CLIの実行ファイル・バージョンを別々に確認する。CLIの結果だけでDesktopの挙動を断定しない。
- ユーザー設定・信頼済みプロジェクト設定・管理設定の有効なルールを確認し、拒否理由を出す規則の所在を確定する。秘密情報や設定全文は診断記録へ出さない。
- 検証を「規則単体の照合」「PowerShellの分解を含む判定」「実際のDesktopからの実行」に分ける。前回の一時検証スクリプトは、この区別に合わせて修正する。
- [host-executables.rules](C:/Users/kazum/.codex/rules/host-executables.rules) のPowerShell本体を禁止する2規則を撤去する。既存のエンコード実行・破壊・公開・実通知などの禁止は保ち、絶対パスで起動する場合も必要な境界が評価されるようにする。
- PowerShell全体への`allow`、自動承認の無効化、独自の常駐審査機構は追加しない。複雑なコマンドは標準の安全審査へ渡す。
- 適用前に変更対象の実バイトとハッシュを退避する。他作業による変更があれば上書きせず再照合する。保存後も旧理由が残る場合は、読み込まれた設定層を調べ、同じ操作を反復しない。

同じ実行エンジンで保護を確認できない場合は設定の切替を保留する。Codex本体の不具合と判明した場合は、最小再現と影響バージョンをまとめるところまで進め、本体の独自改造や未検証更新には広げない。

## 3. 共有監査の停止範囲と診断を直す

先行担当の統合済み修正を最新mainで確認し、足りない箇所だけを既存実装へ追加する。

| 状態 | 扱い |
|---|---|
| 特定の変更・検証に結び付いた失敗 | 影響する変更だけを停止 |
| 現在の変更と無関係だと証明できる監査 | 現在の停止理由に使わない |
| 記録の破損で影響範囲を確定できない | 不明として停止し、原因と復旧経路を示す |
| 検証済みの修復 | 既存の専用経路から統合可能にする |
| 資源・ロックの一時競合 | 該当操作だけ待機し、他作業を継続 |

- `weekly_audit_guard`で例外原因を捨てず、失敗した段階・対象記録・原因分類を保持する。任意の例外本文をそのまま表示せず、秘密情報を含まない識別情報に限定する。
- 現在の停止判定に必要な記録を選ぶ処理と、その証拠の検証を整理する。不正な記録自身の自己申告だけで「無関係」と判定しない。
- `harness_status`と統合処理が同じ判定結果を使い、状態表示と実際の停止理由が食い違わないようにする。
- 内部診断情報は既存の結果型・出力へ追加する。共有キューの記録形式、新しい台帳、監視サービスは増やさない。

## 4. 復旧後の再開とDB依存を接続する

- 既存の再開処理で、監査待ち・資源待ち・検証失敗・実行前の拒否を区別する。実行前の拒否をテスト失敗や実行済みとして記録しない。
- 再開時は対象変更・所有権・検証結果を再照合する。同じ対象に有効な成功証拠があれば再利用し、同じ重い監査を重複投入しない。
- mainや変更内容が進んだ場合は、古い証拠を流用せず必要な再検証へ戻す。
- DB件数不一致は、既存台帳へ対象系列・依存する補完作業・解除条件を記録する。解除には、復旧担当による同一スナップショットでの件数・キー集合・最新日の整合確認を必要とする。
- DB修復、大量補完、他担当PRのマージは引き取らない。他作業のプロセス・ロック・作業コピーも操作しない。

## 5. 検証・適用・完了条件

**コマンド実行**

- 通常の読み取り、Git状態確認、Python検証、監査状態確認がDesktopの通常経路で成功する。
- 危険操作は実行せず、同じ実行エンジンの判定経路で禁止を確認する。
- 実ハーネスの拒否確認には、一時設定で禁止した無害な印字コマンドを使う。単独・複合・PowerShell経由で、禁止部分が実行されないことを確認する。
- 設定の再読込み後にも成功し、一時的な許可やコマンドの書き換えに依存しない。

**監査・再開**

- 既存テストを使い、無関係な変更の通過、影響する変更の停止、対象不明の破損、不正証拠、修復自身の統合経路を証明する。
- 中断後の再開、資源待ち、main更新で、二重実行・証拠流用・他作業への割込みが起きない。
- 実際の共有監査が読み取れ、PR #388の停止理由を現在の状態で説明できる。マージ可否と監査の読み取り復旧は別々に確認する。

実装は所有を確定した外部作業コピーで行い、変更箇所の検証後に必要な品質ゲートを実行して自己所有の変更をmainへ反映する。並行状態は隔離した検証で確認し、他の作業を試験目的で止めない。

**設定保存、検証成功、main反映、実運用での確認を区別し、最後まで確認して初めて完了とする。**

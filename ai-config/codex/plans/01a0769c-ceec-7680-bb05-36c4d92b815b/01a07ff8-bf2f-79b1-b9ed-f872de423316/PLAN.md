# J-Quants・EDINETを正しい最新データで継続運用する改善計画

## 1. 目的と完了条件

現契約・追加費用なしで取得できる全対象銘柄・全データ・最長期間を取り込み、公式データと一致した値をアプリで利用できるようにする。初回の補完だけでなく、新規公表・訂正・取得失敗からの回復まで継続運用に含める。

- EDINETは公表後1時間以内のアプリ反映を目標とする。J-Quantsは各データの公式提供周期に合わせ、利用可能になった更新を追跡する。
- 「取得済み」「保存済み」「アプリ反映済み」を分けて確認する。保存件数や処理の正常終了だけで完了扱いにしない。
- 通常運用はDドライブ。C固定を撤廃し、バックアップ・復元練習は今回行わない。バックアップはNAS準備後の別作業とする。
- 既存のETF等の除外方針を維持する。契約外・公式未提供・取得失敗・未対応項目を区別し、網羅したように見せない。

## 2. 解決する問題と変更内容

| 問題・不足 | 実施する改善 |
|---|---|
| EDINETの通常更新がバックアップ・復元証拠の有無で止まる | 取得・DB反映・財務統合から、この前提条件と専用の開始許可への依存を撤廃する。原本照合、トランザクション、同時更新の排他は残す |
| EDINETは正常保存済みの日を再取得せず、その日の後続公表を見逃し得る | 当日の公式一覧を再照会し、追加・変更された書類と原本を差分取得する。保存済みという理由だけでその日を完了扱いにしない |
| J-Quantsの同名ファイルの訂正を再取得しない | ファイル名だけでなく公式更新日時・サイズ・取得内容のハッシュを管理し、更新版を再取得して下流へ反映する |
| 信用残高の取得値と表示値が違う | 普通株・種類株を分離し、同一資料の買残・売残を組として採用する。最大値による選択と「既存値があれば更新しない」処理を修正する |
| 全銘柄の調整後株価が検証できていない | 分割等の調整情報を含む公式経路で補完し、企業行動によって変わった過去の価格・出来高も再反映する |
| 財務統合が一部銘柄の確認にとどまる | 全対象へ段階的に広げ、期間・連結区分・通貨・単位・開示時点を揃える。原本にない値を推測で補わない |
| EDINETに提出日の不一致がある | 確認済み105書類を起点に全対象を点検し、公式提出日時へ訂正する。影響する財務集計・表示を再生成する |
| 短い遡及期間より古い取りこぼしが残り得る | 直近の再照会と、期間制限で消えない未完了一覧を併用する。長期停止後も最後の完了地点から追いつけるようにする |
| 取得した各データのアプリ利用が不明 | データ別に「取得元→保存先→加工→API→画面」を対応づける。未接続項目は既存の関連画面やデータ確認導線へ接続する |
| 処理成功でも画面が古い場合がある | 財務集計、表示用テーブル、集計ビュー、キャッシュまで更新対象に含め、最終表示の時点で鮮度を判定する |

訂正では過去原本と出典を保持し、現在値だけを適切に更新する。他の情報源の値を無条件に上書きせず、既存の情報源優先順位を維持する。同順位で解決できない不一致は明示する。

## 3. 継続更新とアプリでの見え方

**更新の動かし方**

- EDINETは15分間隔で当日の公表を確認し、変更書類の取得・解析・財務統合・表示更新を連続して進める。
- 日次で直近31日を再照合し、過去期間は週単位の巡回照合で訂正・欠落を確認する。未完了分は期間外になっても追跡を続ける。
- J-Quantsは公式提供時刻と契約上の制限に合わせて差分確認を配置する。一括取得以外の利用可能APIも対象一覧へ含める。
- 最新分の処理を過去分の大量補完より優先する。既存の実行枠・重複防止・進捗記録を利用し、同じ対象への重複書き込みを防ぐ。
- 通信障害・利用制限は待機時間を置いて再試行する。認証・契約・形式不整合は原因別に保留し、無限再試行や成功扱いをしない。
- 実行設定だけでなく、このPCの実際の定期実行登録・実行結果・下流の更新まで確認する。

**API・画面の変更**

既存のAPIと画面を拡張し、データの意味や既存項目を不用意に変更しない。必要な保存項目追加は既存の移行手順に従う。

各データについて、対象日・公式更新時点・最終確認時刻・アプリ反映時刻・未反映理由を確認できるようにする。「最新」「公式更新待ち」「取り込み遅延」「失敗」「契約外」「未対応」を区別する。

問題のある値は正常な最新値として表示しない。最後に確認できた値を残す場合は、その日付と未確認状態を併記する。週次の信用残高を日次更新の株価と同じ基準で古いと判定しない。

## 4. 実施順序と検証

1. **対象と不足を確定する**  
   既存の取得能力情報・実行記録を使い、データ種別×銘柄×期間の取得範囲と未完了を一覧化する。進行中の補完結果を引き継ぎ、同じ大量取得を重複実行しない。

2. **誤表示と通常更新の阻害要因を直す**  
   信用残高の訂正反映、EDINETの不要条件撤廃、当日再取得、訂正版の検出を先に実装する。コードだけでなく関連する運用設定・説明・テストを同時に整合させる。

3. **最新分を通し、全履歴を補完する**  
   最新分で取得から実画面まで確認してから、全銘柄・全期間を再開可能な単位で補完する。各単位で保存値・出典・表示を照合する。

4. **定期運用を確認する**  
   このPCのアプリを更新し、通常起動した画面で確認する。連続7日間と信用残高の次回公表を含む実運用で、更新・訂正・再試行・遅延表示を確認する。

必須の検証ケース：

- 伊藤園の確認済み信用残高が、取得値から両方の関連API・画面まで一致する。
- 同日追加のEDINET書類、訂正報告書、同名の更新ファイルを再取得・再反映できる。
- 普通株と種類株、分割調整、欠損とゼロ、連結と単体、円と百万円を混同しない。
- 重複実行・途中終了・通信障害・長期停止後の再開で、欠落や重複計上を生じない。
- バックアップや開始許可ファイルがなくても通常更新でき、破損原本や不整合データは正常値として通さない。
- 上流だけ成功し下流が失敗した場合、アプリ反映済みとは表示しない。

## 5. 完了の判定と制約

全対象について、取得可能範囲との照合、訂正の反映、APIと実画面の一致、継続更新の確認が揃った段階で完了とする。既知の不足は、銘柄・期間・項目・理由を具体的に残し、未解決のまま全体完了とはしない。

公式サービスの停止やPC停止中まで「常に最新」を保証するものではない。その場合も、遅延を明示し、復帰後に自動で追いつくことを要件とする。

現存するDB内部異常が実際に処理を妨げる場合は、対象と影響を限定して修正方法を示す。これを理由に、通常更新へ一律のバックアップ必須条件を戻さない。NAS設定・認証操作・破壊的なDB修復は今回の通常更新実装と分けて扱う。

# J-Quants・EDINETの定期更新と失敗回復の修正計画

## 1. 目的と現在地

**最新データの取得・保存・アプリ反映を復旧し、過去分の失敗が最新更新を止めない構造にする。** 今回確認した定期更新の障害を対象とし、全履歴統合の完了とは分けて判定する。:codex-annotation{index="1"}

確認できた状況は次のとおり。

- J-Quants日次更新は、取得開始前のDB接続待ちで失敗した。以前の需給APIの接続不足と同じ原因かは未確定。
- 履歴補完は1,104処理が成功したが、空売り残高の保存1件が重複キーエラーになった。コードの重複時更新条件は実DBの主キーと一致しており、原因は追加検証が必要。
- EDINETは12:31更新分の一覧を保存済みだが、アプリ反映記録は9:26。財務統合で連続5回の失敗による自動停止が作動している。ログの「Not Found」は対象日と対応づけ、当日取得の失敗と決めつけない。
- 伊藤園の両需給APIは正常。既存の503対策を維持する。

## 2. 修正内容

### J-Quantsの日次更新と再試行

- 失敗時刻のDB稼働・接続生成エラー・同時起動記録を照合し、DB未起動、接続上限、処理内の接続占有を区別する。
- 日次処理の開始前に、時間制限付きのDB接続確認を行う。一時的な接続失敗は既存の実行管理で1分・5分・15分後の最大3回再試行とし、待機中はDB接続を保持しない。
- 接続できない間も未完了期間を失わず、復旧後は最新分から再開する。成功済みの大量取得を最初から繰り返さない。
- 接続上限やDB全体のタイムアウトを一律に増やさず、原因が確認できた起動・接続保持箇所だけを修正する。

### 空売り残高の重複保存

- 失敗した原本と保存キーを固定し、隔離DBで「初回保存・同じ原本の再保存・訂正版・同時実行」を再現する。報告者、計算日、銘柄、単位、原本の違いを保持する。
- 同一観測の再保存は件数を増やさず、訂正原本は旧版を残す。異なる内容を単純な重複除去や例外の無視で捨てない。
- 隔離DBで再現せず実DBだけで矛盾する場合は、対象テーブル・索引の読み取り検査へ進む。DB内部異常が確認された場合は、この対象の再投入を保留し、限定した修復案を別途提示する。
- 回復対象は失敗した取得単位と関連する未反映分に限定する。

### EDINETの最新分と過去分の分離

- 当日の取得・財務統合・表示更新を先行し、過去分は残りの実行予算で処理する。最新分と過去補完の結果・再試行時刻を別々に記録する。
- 財務統合の連続失敗10件を対象日・書類・例外へ対応づけ、最初の原因を修正する。同じ不整合を持つ過去分は理由付きで保留し、15分ごとに再試行して最新分の処理枠を消費させない。
- 自動停止は、データ不整合のある対象と、DB障害などの共通障害を区別する。共通障害の停止保護は維持し、履歴の個別不良だけで最新分を全面停止させない。
- 「Not Found」は対象日、HTTP状態、公式応答の状態を秘密情報なしで記録する。正常なゼロ件として扱わず、公式提供範囲外と確認できた場合だけ取得不可として分類する。
- 停止解除は原因修正と限定検証の後に、既存履歴を保持して行う。失敗履歴の削除や無条件の停止解除は行わない。

## 3. API・画面と回復手順

- 既存のデータ運用API・画面を拡張し、「最新分の取得時刻」「保存時刻」「アプリ反映時刻」「過去補完の残件」「停止理由・次回再試行」を分けて表示する。既存URLと数値の意味は維持する。
- 当日分が最新でも履歴が未完了なら、その両方を表示する。取得成功だけでアプリ反映済みにしない。
- 修正後は、最新分の少量処理→保存・出典照合→API・実画面確認→失敗単位の再開の順に進める。
- 実Schedulerの登録内容と次回の実行結果を確認する。設定変更が必要な場合も既存登録経路を使い、認証画面を重複して開かない。

## 4. 検証と完了条件

- DBが利用できない状態から復帰したとき、上限付き再試行で追いつき、重複書き込みや接続保持が残らない。
- 空売り残高の同一原本・訂正・同時実行・途中終了で、二重計上や原本の消失がない。
- EDINETの過去日が失敗しても、正常な当日書類は財務統合・表示まで進む。共通DB障害時は安全に待機する。
- 取得成功後の下流失敗、公式未提供、正常ゼロ件をAPIと画面で区別できる。
- 更新中も伊藤園の両需給APIが正常応答し、原本の買残・売残と一致する。
- このPCへの反映後、日次更新・履歴補完・EDINET定期更新の実行成功と下流反映を確認する。その後の連続7日間・次回信用残高公表の検証は、既存計画として継続する。

通常運用はDドライブ。追加費用、Cドライブへのバックアップ、復元練習、NAS設定、認証操作、所有外プロセス停止、破壊的DB修復は今回に含めない。未解決のDB異常が残った場合は対象を明示し、全体完了とは報告しない。

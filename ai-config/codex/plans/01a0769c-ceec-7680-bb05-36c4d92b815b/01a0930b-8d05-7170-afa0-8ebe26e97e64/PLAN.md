# EDINETの取得内容整理と、最新更新を止めない運用への改善計画

## 1. 目的と現在の問題

**当日の開示一覧と財務を優先してアプリへ反映し、PDF・添付等と過去補完は別処理で追いつかせる。取得対象は減らさない。**

現在確認できている問題は次のとおり。

- 当日の定期更新が、公式APIへ問い合わせる前の更新用ロック取得で失敗している。
- 夜間の過去分取得が、9月11日19:40開始のまま実行中と記録されている。実際のロック保持元は未特定。
- 実装上、書類の通信・原本保存中も全体共通のロックを保持するため、過去分が最新分を妨げ得る。
- 未完了記録の置き換えでアクセス拒否が発生した履歴もあり、競合と権限異常を区別する必要がある。
- 財務正規化・本文抽出には別の定期経路があり、先行処理の失敗によって待機している。取得からアプリ利用までの全体像が分かりにくい。

ロックファイルの削除や停止保護の一律解除で解決扱いにせず、原因と影響する処理を特定して直す。

## 2. 何を取得し、何に使うか

既存の説明資料とデータ運用画面を、次の分類に揃える。

| 区分 | 取得内容・分かること | アプリでの扱い |
|---|---|---|
| 公式書類一覧 | 提出者、提出日時、書類種類、対象期間、訂正・取り下げ・公開状態 | 開示一覧、更新検知、原本と財務の出典 |
| 提出本文・監査報告書のZIP | XBRLの数値、期間・単位、本文、注記、監査情報等 | 財務統合、企業ページ、原文確認 |
| PDF・添付・英文・CSV | 書類の閲覧用原本、補足資料、英訳、XBRLのCSV表現 | 原本参照と各抽出処理。保存済みだけで分析済みとはしない |
| 大量保有の構造化データ | 報告者、保有株数・割合、変更、保有目的等 | 保有者・需給の確認。J-Quants経由の取得と公式直接取得を区別 |
| EDINET DBの補助データ | 企業情報、財務の補完、有報本文・事業KPI候補等 | 別サービスの情報として出典と利用範囲を表示 |

金融庁公式APIは書類一覧と書類原本の取得を提供する。閲覧可能期間は書類種別等で異なるため、「全書類を一律10年取得できる」とは扱わない。[金融庁・EDINET API仕様書](https://disclosure2dl.edinet-fsa.go.jp/guide/static/disclosure/download/ESE140206.pdf)

各分類について、**取得元 → 原本保存 → DB保存 → 抽出・統合 → API → 画面**を対応づける。実データから対象期間、最終確認、未完了件数、理由を確認し、未接続・未対応はそのまま明記する。説明資料に残る「大量保有専用」「日次だけ」といった古い記述も修正する。

今回、新しい分析機能や外部サービスは追加しない。既存の補助経路は役割と障害を整理し、公式更新の必須条件にはしない。

## 3. 取得・反映処理の変更

- **ロックを短くする。** 全体共通ロックは未完了記録の読み書きと確定に限定する。通信中は保持せず、同じ書類・原本の重複取得は対象単位の排他で防ぐ。確定時に最新状態を読み直し、別処理の更新を消さない。
- **最新分を独立させる。** 15分間隔の処理は当日の一覧確認と必要原本の取得を優先する。過去補完は直近31日・週次巡回・期間外にも残る未完了一覧から再開し、最新分が待機していれば次の取得単位を開始しない。
- **書類単位で反映する。** 日付全体の原本一式が揃うまで待つ構造を改める。一覧を先に反映し、財務に必要な原本の検証が完了した書類から財務統合へ渡す。PDF等の失敗で正常な財務書類を止めない。
- **完了の意味を分ける。** 「一覧確認」「財務用原本」「財務・画面反映」「原本一式」の状態を分離する。一部原本の取得だけで従来の全体完了記録を作らない。既存の成功証跡は、その証明範囲を保って引き継ぐ。
- **反映をまとめる。** 変更書類の財務統合後、表示用集計をまとめて更新する。取得・解析・集計を同じ原本に対して重複実行せず、途中失敗は未完了段階から再開する。
- **障害を分類する。** 排他競合は再実行待ち、通信障害は上限付き再試行、認証・権限・形式異常は原因付き保留にする。Windowsのアクセス拒否を無条件に競合扱いせず、確認された共有競合だけを短時間再試行する。
- **企業未解決と訂正を扱う。** 未解決企業は書類単位で保留し、公式情報で対応を確定する。訂正・取り下げは過去原本と他情報源を保持したまま再計算する。書類の用途を判定し、財務処理の対象外書類を財務未完了へ混ぜない。

旧処理が稼働中の場合は所有・実行状態を確認し、終了または正式な引き継ぎ後に切り替える。今回の調査だけを根拠に、他のプロセスを停止しない。

## 4. API・画面と検証

既存APIのURLと財務数値の意味を維持し、段階別状態、確認・反映時刻、待機理由、次回確認時刻を追加する。データ運用画面では、最新分と過去補完を分け、金融庁公式・J-Quants経由・EDINET DBを区別する。

必須の検証は以下とする。

- 過去原本の取得を遅くしても、当日の一覧確認と正常書類の財務反映が進む。
- PDFだけ失敗した場合、財務反映成功と原本一式未完了を同時に正しく表示する。
- 同日追加、訂正、取り下げ、企業未解決、公式未提供を区別できる。
- 並行実行・途中終了・通信障害でも、原本・未完了記録を失わず、重複計上しない。
- 権限異常とロック競合を区別し、処理成功や正常ゼロ件へ置き換えない。
- DB保存後に集計が失敗した場合、アプリ反映済みにならない。
- 正常企業の原本・DB・API・実画面が一致し、財務の期間・連結区分・単位を保持する。

## 5. 適用順序と完了条件

最初に取得経路と実行中処理を棚卸しし、ロック保持元・アクセス拒否・先行処理待ちの原因を確定する。その後、最新優先と段階別反映を実装・検証し、このPCのAPI・アプリ・必要な定期実行設定へ反映する。全履歴補完は既存原本と未完了記録を引き継ぐ。

通常運用はDドライブとし、追加費用、Cバックアップ、復元練習、NAS設定、認証操作、破壊的DB修復は今回の実装に含めない。通常更新にバックアップや開始許可を必須とする条件を戻さない。

当日の公式公表から1時間以内の反映を目標とし、連続7日間の更新と、訂正・失敗後の回復を確認する。短期の復旧完了と、全履歴・全項目の統合完了は分けて報告する。

# 財務表の接続安定化と、TDnet訂正の通常取得経路の改善

## 目的と実施順序

対象は、①接続準備表示の再発、②通常のTDnet取得から財務表までの接続の2件とする。①をアプリ反映まで完了してから②へ進む。下期EPSの点検は、計算モジュール変更の完了後に再開する。:codex-annotation{index="1"}

遅延時は、選択いただいた方針どおり**取得済みの財務表を残し、「接続確認中・更新未確認」を表示する**。取得済みデータを最新確認済みとは扱わない。

## 1. 接続状態の判定と表示をそろえる

現行処理には、接続確認の時間切れをDB利用不可として返す経路と、保存済みの状態通知で読取可否を上書きする経路がある。この2つを整理する。

- 接続確認の内部結果を「利用可能」「DB利用不可の応答」「認証エラー」「時間切れ・判定不能」「BFF到達不能」に分ける。既存APIの数値項目や通信形式は変更しない。
- 通常確認、起動時確認、復旧前後の確認を、既存の接続状態管理へ集約する。時間切れだけでDB障害を確定したり、BFFの再起動へ進めたりしない。
- 全体の読取可否は直接の接続確認で更新する。SSEの保存済み状態は監視情報として表示し、読取可否を直接上書きしない。相違がある場合は既存の確認処理へつなぎ、確認要求を重複実行しない。
- 接続先・認証情報が変わった後に返った古い確認結果や、後から到着した古い要求結果は適用しない。
- BFF到達不能の確認期間、既存の再試行間隔、通信時間上限は原則維持する。変更の主眼は時間延長ではなく、結果の分類と状態遷移の修正とする。

画面では、時間切れやDB障害でも同じ銘柄の取得済み表と取得時点を残す。未取得の銘柄には別銘柄の表を流用しない。認証失効・接続先変更時は以前の表を引き継がない。機能単位の保有情報保留は、その機能の問題として表示する。

自動復旧は確認されたBFF到達不能に限定する。BFFが応答している場合は接続確認を続け、DB利用不可や認証エラーをBFF再起動で解消しようとしない。

## 2. TDnetの通常取得から採用・表示までを検証する

summary保存時と財務統合時の採用処理は実装済みなので、その接続を再利用する。

- 既存の `earnings-tdnet-intraday-refresh` → `earnings-financial-intraday-refresh` の定義・実行記録・保存結果を照合する。`reference-only` はDB書込みを伴うため、調査目的で共有環境へ実行しない。
- 既存の3原本を隔離DBで通常の抽出・保存経路へ入力し、原本情報、summary、正規化、採用、BFFの財務表・履歴・出典までを通す。中間の保存・採用処理をすべてmockに置き換えない。
- 原本情報の受け渡し漏れ、保存失敗の見落とし、増分対象の選択漏れがあれば、その接続だけを修正する。対象期間が抽出されても必要情報が不足する場合は、理由を残し、採用成功とは扱わない。
- 保存・採用に失敗した場合は、既存の終了状態と取込記録へ失敗または部分失敗を伝える。再実行時の重複と、訂正前の値の復活を防ぐ。
- 公表日時による訂正選択、5項目の同一版採用、nil・削除・競合の扱い、過去時点の分析保持は維持する。新しいテーブルや汎用基盤は追加しない。

共有環境では、保存済みの通常実行記録を読取専用で追跡する。自然な訂正取得の実績がなければ「通常経路の隔離検証済み・自然取得の訂正実績は未確認」と分けて記録する。全銘柄再処理やScheduler変更は含めない。

## 3. 検証と受入条件

**接続・画面**

- 2秒・3秒の確認時間を超えて成功する場合、取得済み表が消えず、不要な復旧が起動しない。
- 古いSSE状態や要求結果で、新しい接続成功が取り消されない。
- 本当のDB利用不可、BFF停止、認証失効を区別できる。
- 復旧後に必要な再取得が行われ、要求の重複や再取得ループがない。
- 通常起動したアプリで3300・3662・6118を2巡して切り替え、再取得と出典展開を確認する。確認時間・回数を記録し、将来の無再発を保証したとは書かない。

**TDnet**

- 3300は訂正後の純利益20.45億円・EPS286.59円を維持し、訂正前も根拠から参照できる。
- 3662は通期の売上229.97億円・営業利益10.95億円・純利益3.59億円・EPS19.36円を維持する。
- 6118の既存Q1と対象外データは不変。
- 古い原本の後日再処理、同日訂正、重複実行、訂正版nil、会計条件不一致、出所競合、保存失敗後の再実行を、既存テストを再利用して確認する。

## 4. 統合・記録と変更境界

各改修は対象検証、必要な独立レビュー、正式な品質確認、通常統合を経て、必要なBFF/Desktop更新と実画面確認まで行う。計算モジュール担当と所有ファイルを照合し、同じ箇所を並行編集しない。

共有DBへの追加適用が必要になった場合は、対象・退避・隔離復元・適用前差分確認を具体化する。以前の3原本への承認を、新しい対象への書込みに流用しない。

全体計画書の冒頭・課題表・変更履歴・今回の実績節へ「問題・変更・検証・共有適用・アプリで使える状態・残件」を更新する。接続改善とTDnet運用確認は別々に完了判定し、順序1・2全体やQwenの完成とは分けて記録する。

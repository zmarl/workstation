# AGENTS・Skillの指示整合と自律実行の改善計画

## 1. 目的と再評価した方針

承認済みの通常作業は、調査・実装・対象検証・依頼された利用確認まで続け、意味や外部影響が変わる判断だけをユーザーへ戻す状態にする。過去3回のレビューを統合し、後から修正・撤回した案は最新版で置き換える。

- 指示を追加し続けず、矛盾する原文の置換・重複削除・適用条件の限定を優先する。
- Ready gate、共有DB・実通知・公開・認証・所有外資源の保護、運用再実行の回数制限は維持する。機械的な禁止設定は緩めない。
- 通常作業の裁量と、外部操作の権限を区別する。「既存承認を再利用する」を包括的な許可へ広げない。
- 新しいゲート・監視・常設台帳・役割は作らない。今回の限定修正を、ハーネス凍結全体の解除にしない。

## 2. 修正内容

| 対象 | 実施する変更 |
|---|---|
| **個人・リポジトリの共通指示** | 調査・相談は会話で回答し、保存は依頼範囲に含まれる場合だけ行う。必読文書を作業内容に応じて選ぶ。確認は結果・互換性・データ・外部影響を変える未決事項に限定し、内部名やテスト配置では求めない。アプリ利用の依頼は通常導線で使える確認まで続ける。 |
| **worklog・承認記録** | 直接の実装依頼を承認根拠として記録できる書式にする。独立した承認回答・Echoは実際に確認した場合だけ記録し、日時不明は不明とする。書式を埋めるための質問をなくす。 |
| **運用診断・Scheduler** | 調査／修復／運用再実行を区別する。対象タスクはログとmanifestから特定し、複数候補が残る場合だけ質問する。修復依頼はコード修正と隔離検証まで続ける。再実行は既存承認の対象・影響・回数が一致する場合だけ行う。Schedulerは人手操作後に安全に終了を観測できれば読み取り検証へ進み、登録だけでタスク全体をdoneにしない。 |
| **統合・所有・機械的禁止** | worktree作成やSkillの参照を、commit・公開・mergeの承認と解釈しない。承認済み統合は既存helperで完遂する。会話上の承認と機械的禁止が衝突したら、同じ承認を再要求せず不一致を説明する。DBの「掃除」は所有確認と競合操作の延期に置き換え、所有外接続の終了を許可しない。 |
| **Skillの適用条件・参照文書** | worklog、朝チェック、コンポーネント生成、深いバグ診断の説明文を本文と一致させる。旧stubの一括必読を条件付き参照へ直す。UIガイドの初回構築手順を参考例へ降格する。凍結中に使わない復旧手順は現行の選択肢として表示しない。BFF参照テンプレートの一律・重複検証を既存の対象検証へ統一する。 |
| **Matt Pocock：TDD・診断・レビュー** | テスト箇所の一律承認をなくす。再現手段を作るためのコード読解・暫定仮説を許容し、未検証と明記する。レビューからセットアップを自動起動しない。PRと作業中差分を区別し、未commit・対象の新規ファイルを取りこぼさない。要求は現在の依頼・既存仕様から確認し、不足しても独立して進められるレビューは続ける。 |
| **Matt Pocock：調査・試作・設計・競合解消** | 委任・保存・本実装への反映・commitを一律必須にしない。既存の文書体系を使う。grillingは重要な未決事項に集中し、議論から実装へ移る確認は保持する。競合解消では所有する明示パスだけを扱い、両立しない意味変更を勝手に選ばない。 |
| **Ponytail** | `full`と最小実装の方針を維持し、要求の省略、3行制限、既存テスト基盤の禁止を除く。通常本文と読み込み失敗時のfallbackを整合させる。常時注入されても、通常の質問・文章・投資分析にコード作業の手順を強制しない。 |
| **役割・モデル管理・外部アプリ** | reviewerは独立した受入条件の未証明をすべて報告し、各問題の追加検証案を最小化する。モデル比較・状態調査は読み取りで行い、書き込みを伴うsyncを前提にしない。Canva等の編集・保存と、他者へのコメント返信の承認を分離する。 |

製品API・DBスキーマ・投資ロジックは変更しない。変更するインターフェースは、Skillの起動条件、承認記録の書式、レビュー対象の選び方、報告・完了条件である。

## 3. 編集元と実施順序

1. **変更前の状態を固定する。**  
   最新main・同種作業・所有競合を確認し、実装開始後に専用worktreeとFull worklogを作る。過去の全指摘について、修正先・統合先・撤回済みをworklog内で対応づけ、取りこぼしを防ぐ。個人ファイルは変更対象だけを非公開でバックアップし、元内容のhashを保持する。

2. **共通指示とリポジトリ側を先に揃える。**  
   AGENTS、OWNER_INTENTの関連運用記述、Skill、テンプレート、役割定義、参照ガイドを整合させる。採用内容は既存ODR-0035への日付付き追補とworklogへ記録し、以前の承認記録は保持する。Claude用Skill stubは正規generatorで再生成する。

3. **個人用Skill・プラグインを更新する。**
   - Matt Pocockは既存編集元 [mattpocock-skills](/C:/Users/kazum/plugins/mattpocock-skills) を更新し、既存のpersonal marketplaceから再インストールする。
   - Ponytailは現在の4.9.0を基に [ローカル編集元](/C:/Users/kazum/plugins/ponytail) を用意する。出典・ライセンス・既存機能を保持し、必要な本文とfallbackだけを修正する。personal版へ切り替え、元の配布版は復旧用に保持して無効化し、二重注入を防ぐ。自動更新は追加しない。
   - Canvaのcacheや公式プラグインは編集せず、個人AGENTSの外部送信ルールで適用する。モデル管理は既存の個人AGENTSとModels側の指示を揃える。
   - marketplace更新・再インストールは既存の公式helperを使い、cacheの直接編集を成果物にしない。

4. **検証・独立レビュー後に反映する。**  
   指示と承認境界を扱うため、独立reviewerを1回使う。リポジトリの同じcommitと、個人変更・プラグイン候補の同じhashを渡す。必要なReady証拠を揃え、標準helperでPR・merge・main同期まで進める。個人側は検証済み候補だけを適用し、新規セッションで確認する。

## 4. 検証

文言を固定する新しい常設テストは作らない。構文検査、既存の対象テスト、使い捨て環境での代表ケースを使う。

| ケース | 確認する結果 |
|---|---|
| 調査だけ・意味を変えない局所訂正 | 不要な保存、worklog、全体調査、確認を追加しない |
| 承認済み実装・TDD | 内部名・テスト箇所の承認待ちをせず、実装と対象検証まで進む |
| 原因不明・再現困難な不具合 | 暫定仮説とコード調査を進め、未検証を成功扱いしない |
| PR・未commit差分のレビュー | 正しい比較対象を選び、新規ファイルを含む対象差分を確認する。セットアップを起動しない |
| 試作・用語相談・grilling | 依頼された成果で止まり、本実装・保存・公開へ勝手に進まない |
| 承認済み運用再実行 | 承認を再要求せず、対象・副作用・回数を守る。機械的禁止を迂回しない |
| DB適用・Scheduler・公開・他者への返信 | 必要な明示承認と人手境界を保持する |
| 所有外差分・接続・processの競合 | 他者資源に触れず、競合する操作だけを延期する |
| 複数の未証明な受入条件 | reviewerが独立した問題を省略しない |
| Ponytailの開始・再開・子agent・fallback | 修正文面が入り、旧制約や二重注入がなく、fullと明示的な停止指定が機能する |

- Markdown/frontmatter・JSON・TOML、Skill stubの整合、変更箇所に対応する既存チェックを実行する。
- Ponytailは既存hookテストを隔離環境で使う。汎用plugin validatorが現在のhook manifestを扱えない点は記録し、validatorやhook要件を弱めず、現行CLIの受入とhook実行で別途確認する。
- Rulesは変更せず、既存の引数照合で運用禁止と通常buildの境界が維持されることを確認する。
- 実通知・共有DB更新・実公開を検証のために実行しない。代表ケースは模擬入力・使い捨て環境で確認する。

## 5. 完了条件と復旧

- 採用された全指摘に修正先または明示的な統合先があり、前に撤回した権限緩和案が復活していない。
- リポジトリ変更のmerge・main同期、個人ファイルの適用、プラグインのインストール・有効化をそれぞれ確認する。
- 新規CLIセッションとCodexアプリの新規セッションで更新内容を確認する。既存タスクへ遡及したとは扱わず、他タスクを停止・再起動しない。
- hookの信頼確認などアプリが要求する人手操作が残る場合は、その操作だけを示し、「適用済み・実効確認待ち」と報告する。文面の変更やインストールだけで完了にしない。
- 問題が出た場合は、所有する変更だけを戻す。プラグインは直前の版・有効状態へ復旧し、個人ファイルは適用後の他者変更がないことを確認してから戻す。
- 復旧手段と残る制約を最終報告に残す。常設の監視・自動修復・自動更新は追加しない。

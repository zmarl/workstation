# Flash Nextによる初回決算分析の実装・運用計画

## 1. 目的と今回の方針

**Flash Nextの導入を前提に、公式資料の読取りから数値確認・計算・分析・通常アプリでの閲覧までを完成させる。** 現在のPCで検証し、品質を満たした実測結果から処理時間と運用条件を決める。

過去に決めた分析範囲を引き継ぐ。主要業績、全セグメント、会社KPI、会社予想、資本政策、BS・CF、会社説明、反証、不明点を対象とし、個別の詳細と全社の統合分析を残す。後着資料は新版にし、初回の判断を上書きしない。

現在の候補実装は未統合で、全工程の品質合格と通常運用は未達。Flash NextがQwen4の構造の実験的プレビューであることは公式に確認できるが、将来の互換性や決算分析の品質は今回の実測で確認する。[Qwen公式](https://github.com/QwenLM/Qwen3.8-Flash-Next)

## 2. 読取り方式は二つを比較して決める

過去のPaddle評価では、2社の選定した金額16件・率4件の値と行列、会社説明・留保9件の意味を保持できた。一方、単位・期間との結合は未完成だった。OCRを独立した確認役として残し、Flash Nextとの分担を検証する。[過去の原本評価](D:/Dev/Investment-rtx5000-fp8-thinking-evaluation/data/runtime/evidence/rtx5000-fp8-thinking-evaluation/paddle-layout-gold-comparison-01/summary.md)

| 比較する方式 | 処理の流れ |
|---|---|
| OCRから始める | 原本抽出・Paddle → Flash Nextによる独立した原本確認 → 検証・計算 → Flash Nextによる分析 |
| Flash Nextから始める | Flash Nextによる原本読取り → Paddle等による独立した数値確認 → 検証・計算 → 同じFlash Nextによる分析 |

両方式で次を共通にする。

- XBRL・HTML・PDFから直接取得できる本文・数値・位置情報を先に保存する。取得済みの全文や表を、モデルに何度も生成させない。
- 独立確認には先行モデルの回答を見せない。全ページの確認を保ち、不一致や不鮮明な箇所を拡大再読する。
- 数字だけでなく、指標、会社、当期・前年、単位、連結範囲、注記との対応まで照合する。
- 計算後の分析には、確認済み数値と原文を渡す。却下した候補値が会話履歴から再利用されないよう入力を組み直す。

**同じFlash Nextを常駐させ、読取りと分析に続けて使う構成を基本にする。** アプリが途中で計算モジュールを呼べばよく、モデル自身による自由なツール操作は初期実装に追加しない。[対応サーバーの仕様](https://github.com/ggml-org/llama.cpp/blob/v0.4.0/tools/server/README.md)

採用は、誤った数値・条件の採用がないことを必須とし、情報の回収、重要論点の網羅、出典・留保・反証の正しさを優先する。同等の品質を満たした構成では、起動・再読・修復・保存を含む全体時間で選ぶ。両方とも不合格なら、問題を修正して再評価する。

## 3. 現在のPCでのモデル配置

初回の実機候補は、固定版の **Flash Next GGUF `UD-IQ4_XS`＋画像用mmproj、llama.cpp v0.4.0** とする。配布物は約87.25GiBあり、実際の配置と起動時の使用量を確認してから入力容量を決める。[固定版の配布物](https://huggingface.co/unsloth/Qwen3.8-Flash-Next-GGUF/tree/38bb39ee97821de2c9009abb7e93950eec396e66)

| データ | 初期の配置方針 |
|---|---|
| 原PDF・画像・抽出本文 | ファイルと通常RAMに保存する |
| モデルの計算本体 | GPUに配置する |
| N-gram記憶表 | モデル自身の固定データとしてRAM配置を検証する |
| 読んだ入力の一時記憶・画像処理領域 | GPU容量を実測して確保する |

- 共通モデル管理で既存ファイルを照合し、取得版と保存先を固定する。
- 短い文章、実際の長さの決算資料、画像、連続処理の順に、ロード時と処理中のRAM・VRAM使用量を測る。
- 読み取った資料をRAMへ保存することと、計算本体をCPUへ退避することを分ける。本体のCPU退避は初期構成に含めず、必要と判明した場合に条件変更を相談する。
- Flash Nextを工程ごとに再起動しない。入力の再利用効果は実測し、画像や全文の再処理が省けるとは先に仮定しない。
- 初期エンジンで未対応のMTPは成立条件にしない。対応構成の高速化比較は、基本経路の品質確認後に行う。
- 既存プロセスの所有を確認し、検証に必要な空き資源を確保できる条件で実行する。

## 4. 実装する内容と順序

**最初に一社の「原本→計算→Flash Next→画面」を通し、その接続を分析範囲全体へ広げる。**

1. **既存実装の引継ぎと資料の固定**  
   未統合の初回分析実装を確認して再利用する。原本、公開・取得時刻、資料の役割、訂正関係、全ページの処理状況を固定し、既存の失敗記録を保持する。

2. **ページをまたぐ条件の対応付け**  
   会社・年度・単位・会計条件・注記を、それぞれが適用される表・列・セルへ結ぶ。全文JSONの字面の違いで文書全体を失格にする扱いを改め、不一致が影響する範囲を保留する。影響範囲が分からない注記は保留を維持する。

3. **計算への接続**  
   まず売上・原価・粗利・販管費・営業利益で通し確認し、続いて経常利益・純利益・EPS、セグメント・KPI、会社予想、BS・CFへ広げる。既存Compilerを再利用し、補助計算に残る固定月などの前提を解消する。分析には表示用に丸める前の計算値を渡す。

4. **原因分析と全社統合**  
   確定した変化、会社説明、算術的な分解、原因仮説、支持・反証、不明点を分ける。入力不足を未開示へ変換せず、一般論の仮説を増やして不足を埋めない。個別分析が完成した段階から閲覧でき、統合に失敗しても個別結果を残す。

5. **既存アプリと通常運用への接続**  
   既存の初回分析の保存形式・BFF応答を拡張し、項目別照合、資料の確認範囲、工程別モデル、未完了理由を渡す。既存の計算結果インターフェースと旧保存版の閲覧を維持する。新規イベントを既存workerで受け付け、再起動後も保存済みの進捗から続けられるようにする。

モデルを将来交換するときは、実行設定・読取り部分・品質評価を差し替え、計算と保存・表示の契約を再利用する。Qwen4の未公開仕様に合わせた機能は先回りして作らない。

## 5. 検証と運用開始の条件

- **原本と数値**：6118のページ間条件、4707の小さな利益率差、6654の単位・文字化け、7944の本体と後日通知を確認する。前年値への置換、千円と百万円、ゼロと横棒、他社引用、訂正の遡及混入も検証する。
- **比較資料**：既存の調整用12社・未使用12社を基礎にする。正解表と必須論点を原本から整え、調整に使った会社を未使用評価へ数えない。原因分析単体の比較には、同じ確認済み数値・原文を渡す。
- **分析品質**：原本にある重要情報の脱落、会社説明の留保落ち、出典と主張の不一致、仮説と反証の矛盾を確認する。形式上の正常終了を品質合格にしない。
- **継続処理**：長い資料、資料切替、キャンセル、時間切れ、保存失敗、再起動を確認する。未完成を完成扱いせず、必要資料を切り捨てて時間内に収めない。
- **利用者の確認**：このPCの通常アプリで、現在のBUILD・BFF・Flash Nextの接続を確認し、新しい対象イベントの受付から生成・保存・読戻し・原ページ表示まで実証する。

処理時間の締切は先に置かない。品質を満たした後に、起動込み・常駐時の時間、処理件数、待ち行列の増減から運用条件を決める。全対象を処理する方針を維持し、優先度は処理順に使う。

数値表だけの成功、モデルの起動成功、ビルドや統合の成功は途中段階とし、**通常アプリで新規決算の一連の処理が成功したことを、最初の運用成立として記録する。**

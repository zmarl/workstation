# 統計データの全対象整備・継続運用 実装計画

## 1. 到達目標と前提

**計画書に記載した必要項目を全件管理し、取得可能なデータについて「公式値との一致・必要履歴・改定保全・定期更新・通常アプリでの利用」を揃える。** 全国指数だけで作業を終えず、日米共通統計、33業種、関連する海外統計まで段階的に進める。

全国IIPの原本・改定保全、2000年以降の履歴補完、通常アプリへの供給は既存の成果として引き継ぐ。

- 新規取得先の追加費用はゼロ。既存契約と既存の取得器・保存先・再取得キュー・画面を使う。
- 「全対象」は計画書の必要項目を意味する。各機関が公開する全表・全分類の無差別取得は行わない。
- 無料取得不能、公式未提供、利用条件未確認の項目も分母に残す。代理指標や推計値で取得済みにしない。
- 主要月次・四半期は2000年以降、業種・品目詳細は直近10年。開始時期・基準変更による断絶は明示する。
- 財務・開示は共通保存基盤への影響を扱い、個別の復旧作業は既存担当の範囲を維持する。

## 2. 実装順序と各段階の成果

| 順序 | 実装内容 | 完了条件 |
|---|---|---|
| 1：検証・保存基盤の安定化 | 検証workerが異なるPython環境を使う問題を修正し、最終証拠を後片付け前に保全する。統計保存先の読取り不一致を再検証し、DB復旧担当へ対象と証拠を接続する | 同じ版の検証から証拠保存・通常の統合まで成功。大量補完する保存先で件数・キー集合・値が一致 |
| 2：必要項目の全件確定 | 日米共通統計と33業種の観測項目を、具体的な系列・単位・対象分類へ分解して既存カタログに登録する | 必要項目すべてに取得経路、必要期間、供給先、到達状態または未達理由がある |
| 3：既存経路の正確性修正 | PMIと代理指標の分離、改定版の選択、公表日時、欠損・鮮度判定、全国・業種別の表示定義を修正。IIP・機械受注の既存復旧成果を取り込む | 定義・値・改定・公表時点の検証が通り、誤った値や状態を公開しない |
| 4：日米共通統計の充足 | 既存取得器への設定追加を優先し、不足する公式API・ファイル経路を追加。最新期間を確保してから履歴を分割補完する | 日米の必要項目について、取得可能な最新値・必要履歴・出典が揃い、残る不足を説明できる |
| 5：33業種・海外の充足 | 半導体・機械・自動車、素材・資源・建設、消費・物流・サービス・金融の順に整備する | 各業種の必要観測項目と関係国を網羅し、代理指標との違い・取得不能理由を追跡できる |
| 6：運用・アプリへの定着 | 各まとまりを定期収集・再取得・監視・通常画面へ接続し、次の実公表・改定への追随を確認する | 定期実行だけでなく、公表後の更新と通常アプリへの到達が実測で確認できる |

段階6は各まとまりの完成ごとに実施する。全対象の整備中も、検証済みのデータから利用可能にする。

## 3. 取得・保存・網羅性の実装

### 必要項目と取得経路

既存の `shared/catalogs/sector_kpi_requirements.yaml` と履歴・系列カタログを拡張する。別の進捗台帳は作らない。

- 「生産量・資源価格・採掘コスト」のような複合要件を独立した観測項目へ分ける。価格指数だけで数量まで充足したことにしない。
- 系列ごとに作成機関、配信元、公式コード、国・地域、分類、頻度、単位、基準年、季節調整、名目・実質、必要期間、利用条件、保存先、表示先を対応づける。
- 日米共通統計は計画書の全項目を対象にする。日本は既存e-Stat・統計ダッシュボード・日銀・府省ファイル、米国は既存FREDを優先し、不足分を作成機関の公式経路で補う。
- 中国・欧州は主要統計、台湾・韓国は半導体関連の生産・在庫・輸出・受注を対象にする。企業売上と政府統計は別系列にする。
- 品目別貿易は、業種の必要項目に対応する品目・相手国を登録して取得する。金額、数量、数量単位を保持し、分類改定の前後を無条件に接続しない。

### 正確性と履歴

- 公式応答・ファイルを既存原本保存領域へ保存し、内容ハッシュ、取得条件、取得時刻、実行記録と結ぶ。秘密情報は除外する。
- 値だけでなく、注記・速報区分・定義の変更も改定として保持する。同じ内容の再取得や取得範囲の変更だけでは改定を増やさない。
- 保存済み改定履歴から最新版を一意に選ぶ。取得・処理順序によって古い版が最新版へ戻る経路を修正する。
- 公表日時を観測日・取得日時から生成しない。既存の疑わしい公表日時は対象を特定し、公式根拠が取れるものだけ訂正する。元記録は残す。
- 前年比・前期比などは原系列も保持する。履歴開始時点の計算に必要な先行期間も取得し、比較元欠損やゼロ除算を正常値に置換しない。
- 履歴補完は系列・期間単位で再開可能にする。書込み前に件数・期間・定義を検証し、失敗した単位だけ保留する。

DB不整合が確認された対象は、復旧と読取り一致の証明まで大量補完を止める。健全な別系列の整備は継続する。

## 4. 継続運用とアプリへの供給

### 更新・監視・再取得

- 鮮度の主判定を、公式に公開済みの最新期間と保存期間の差にする。公表予定だけを公開済みの証拠にしない。
- 未公表、配信遅延、通信・認証・上限、形式変更、内容不一致、保存不整合、アプリ未接続、未提供・条件未確認を区別する。
- 通信など再試行可能な失敗は既存キューへ系列・期間を指定して登録する。定義変更・品質不一致・DB不整合を無条件再試行しない。
- 公式公表の翌営業日までの追随を目標にする。提供元の公表時刻・休日を考慮し、運用画面では日本時間に統一する。
- 監視未登録と無効化予定タスクの残存を再照合する。統計に関係する実行元・監視・復旧先を一致させ、他領域のタスクを一括変更しない。
- 不合格データは公開せず、最後に確認済みの値と古さを残す。原本と失敗理由は調査できる状態で保持する。

### API・画面の変更

既存の統計一覧・詳細・運用情報APIを拡張し、新しい画面経路は増やさない。

- 必要履歴、保存期間、公式最新期間、改定状態、欠損理由、最終確認時刻を既存の品質情報に追加する。追加情報がない既存系列は「不明」として互換性を維持する。
- 全国・業種別、原指数・季節調整値、実統計・代理指標が一覧と詳細の両方で識別できる表示にする。
- 「公表時点を再現できない」と「観測月が欠けている」を別に表示する。
- 全国指数が1本あるだけで各業種の詳細統計まで充足したように見える集計を修正する。
- 網羅性は、必要系列・必要期間・公式最新期間への追随・出典と定義・アプリ参照可否の5軸で表示する。

## 5. 検証・反映・完了判定

各実装単位で、次を確認してから通常アプリへ反映する。

1. **定義と値**：同じ分類・単位・季節調整・改定版の公式値と保存値が一致する。
2. **改定と再実行**：同月訂正、注記変更、応答順変更、中断・再開で旧版消失や二重反映が起きない。
3. **欠損と遅延**：未公表、配信遅延、欠測、形式変更を区別し、不正な値を公開しない。
4. **保存と供給**：原本→DB→API→普段のアプリで、値・期間・出典・品質表示が一致する。
5. **運用**：定期実行と対象再取得が成功し、次の実公表・改定後にも更新される。

関連テストと実データ照合から開始し、変更範囲に応じた最終検証を行う。証拠の保存・受け渡しを復旧し、前回の代替統合を通常手順にはしない。

「実装済み」「運用接続済み」「実公表追随確認済み」を分けて管理する。無料取得不能や未提供を含む全必要項目の扱いが確定し、取得可能な項目が上記条件を満たした時点で、全対象整備の完了を判定する。未取得項目が残る場合は「全データ取得完了」とは表記しない。

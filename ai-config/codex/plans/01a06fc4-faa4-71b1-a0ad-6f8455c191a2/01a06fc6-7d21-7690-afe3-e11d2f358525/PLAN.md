# 統計データ収集・共通基盤整備計画書案

## 1. 目的と現在地

**既存の収集処理を土台に、取得値の正確性、必要データの網羅性、更新の継続性を段階的に高める。** 最初に既存経路の欠損・改定管理・鮮度判定を整え、その後に日米の主要統計と海外の産業別統計を拡充する。

対象はマクロ・産業統計と、財務・開示にも共通する収集基盤。新規取得先は追加費用ゼロとし、既存契約は維持する。統計は企業・業種・決算を読む参考情報として提供する。

### 2026年9月5日の確認結果

| 領域 | できていること | 残っていること |
|---|---|---|
| 全国の鉱工業生産指数 | 統計ダッシュボード経由の取得処理が既に存在。DBで2026年7月分まで確認。季節調整値104.7、原指数110.6 | 改定前の値の保全と、長期履歴の充足確認 |
| 業種別の鉱工業指数 | 製造工業全体・生産用機械・輸送機械・化学・鉄鋼について、生産・出荷・在庫・在庫率の取得経路が存在 | 今朝の取得記録では4活動とも2026年3月分まで。古さを検出して更新を停止しており、全国指数の最新化だけでは解決しない |
| 日本のその他統計 | e-Statの統計表探索、分類情報、期間分割取得、日銀の系列カタログ・履歴取得が存在。主要なCPI・失業率はDBで7月分まで確認 | 同じ保存先の景気・消費関連には1〜2月で止まった系列もある。別の保存先・表示経路も含めた系列単位の照合が必要 |
| 米国・海外マクロ | FRED等の既存経路があり、米国雇用は8月、CPIは7月の観測値をDBで確認 | 日米の必要項目全体を充足しているとは未確認。PMIと代理指標の区別、古い系列の扱いも整理が必要 |
| 業界統計 | 工作機械、鉄鋼、建設、小売などの取得器、TSMC月次売上、韓国半導体輸出の履歴取得経路が存在 | 直近の業界統計収集は一部成功。BDIの取得は失敗している。利用条件の確認待ちで保留中の系列もある |
| 共通運用 | 取得実行記録、再取得キュー、取得元登録、鮮度監視、業種との対応表が存在 | 実行された取得元のうち監視側に未登録が9件。無効化予定の定期タスクが実環境に7件残存 |
| 改定・公表時点 | 一部に版情報や、当時の値を再現できるかを示す仕組みがある | 同月訂正で旧値を上書きする経路、公表日と取得更新日を混同する経路がある |
| アプリへの供給 | 統計一覧・詳細を提供する既存APIと画面がある | 今回の運用情報APIはタイムアウト。通常アプリでの表示・接続状態は未検証 |

**現状は「収集基盤があり、最新化できている系列もあるが、全体の正確性・網羅性・継続運用は未達」である。**

参照会話からは方針を引き継ぐ。ただし、会話で提案された統計ダッシュボードの追加は既に実装されているため、新設項目にはしない。会話内の添付資料本体は未取得であり、以下の詳細は会話本文・現行実装・公式仕様から再構成した計画とする。

## 2. 収集範囲と優先順位

### 日米を共通基盤とする

| 対象 | 揃える項目 | 取得方針 |
|---|---|---|
| 日本の共通統計 | GDP、物価、雇用、賃金、家計消費、商業販売、機械受注、設備投資、住宅・建設、貿易、金利・信用 | e-Stat、統計ダッシュボード、日銀、各府省の公式ファイルを使い分ける |
| 日本の産業詳細 | 業種別の生産・出荷・在庫・稼働率、受注、販売数量、投入価格、品目別・相手国別貿易 | 既存取得器を拡張し、企業の需要・価格・在庫・設備投資との関係が説明できる粒度まで取得する |
| 米国の共通統計 | GDP、CPI・PCE・PPI、雇用・賃金、消費、生産・稼働率、受注・在庫、住宅・建設、金利・信用、貿易 | 既存FRED経路を点検し、足りない詳細をFRB・BLS・BEA・Census等で補う |
| 中国・欧州 | 生産、物価、消費、貿易、金融環境の主要系列 | 最初は主要系列に絞り、関係する業種の詳細を後から追加する |
| 台湾・韓国 | 電子部品・半導体関連の生産、在庫、輸出、受注 | 半導体・機械の整備段階で優先する。企業売上と政府統計は別系列として保持する |
| その他の国 | 対象企業の販売、生産、調達、競合供給に関係する統計 | 具体的な事業上の関係が確認できた場合に追加する |

統計ダッシュボードは登録不要の公式APIだが、必要な業種別詳細まで揃うとは限らない。FREDは、統計作成元・定義・更新を確認できる系列では本番の配信経路として利用する。FRBもG.17の配信先としてFREDを案内している。［統計ダッシュボード仕様］(https://dashboard.e-stat.go.jp/static/api)、［FRBの配信案内］(https://www.federalreserve.gov/Releases/g17/download.htm)

米国の詳細候補は、BLSの労働・物価、BEAの所得・産業、Censusの製造業・販売・在庫・住宅、EIAのエネルギー統計とする。無料登録やAPIキーが必要な経路は、利用準備も導入条件に含める。［BLS］(https://www.bls.gov/developers/)、［BEA］(https://apps.bea.gov/api/signup/)、［Census］(https://www.census.gov/data/developers/data-sets/economic-indicators.html)、［EIA］(https://www.eia.gov/opendata/index.php/api)

### 全33業種の不足を整理し、詳細収集は順番に進める

下表は調査対象の割り当てであり、すべて取得可能・取得済みという意味ではない。各業種について、必要項目、既存系列、欠損、関係国、無料取得の可否を整理する。

| 業種 | 主に補う観測項目 |
|---|---|
| 電気機器・精密機器 | 電子部品の生産・在庫・輸出、設備需要。台湾・韓国・米国を優先 |
| 機械 | 国内外受注、設備投資、機械輸出、顧客産業の生産・稼働率 |
| 輸送用機器・ゴム製品 | 地域別の自動車生産・販売・輸出、部品需要、投入価格 |
| 化学・鉄鋼・非鉄金属・金属製品・ガラス土石製品 | 生産・出荷・在庫、製品・原材料価格、建設・自動車等の需要 |
| 鉱業・石油石炭製品・電気ガス業 | 資源供給、燃料輸入、在庫、電力需要・発電構成 |
| 水産農林業・食料品 | 生産・収穫、卸売価格、輸入数量、食品消費 |
| 繊維製品・パルプ紙・その他製品 | 品目別生産・出荷・在庫、消費、輸出入、投入価格 |
| 医薬品 | 医薬品生産・輸出入、医療需要。承認・薬価情報は既存の別領域と接続 |
| 建設業・不動産業 | 建設受注、着工、工事費、販売・在庫、賃料・金融条件 |
| 陸運業・海運業・空運業・倉庫運輸関連業 | 貨物量、旅客数、港湾取扱量、倉庫在庫、燃料費 |
| 卸売業・小売業 | 業態別販売、販売数量、在庫、家計消費、輸入価格 |
| 情報通信業・サービス業 | サービス活動、関連需要、雇用・賃金、設備投資 |
| 銀行業・証券商品先物取引業・保険業・その他金融業 | 金利、貸出、預金、信用環境、資金調達・市場活動 |

詳細整備の順序は、**半導体・機械・自動車 → 素材・資源・建設 → 消費・物流・サービス・金融**とする。日本の貿易統計は9桁の統計品目番号と相手国まで扱えるため、関係品目を選んで数量と金額を取得する。［税関のデータ案内］(https://www.customs.go.jp/toukei/sankou/howto/gaiyou.htm)

履歴の基本範囲は次のとおりとする。

- 主要な月次・四半期統計：2000年以降。
- 詳細な業種・品目統計：直近10年。
- 日次の金利・金融統計：既存履歴を維持し、共通分析に必要な期間を補完。
- 統計の開始時期や基準変更で連続比較できない場合：取得可能期間と断絶を明示し、補間して埋めない。

## 3. 正しく取得するための共通基盤

### 系列の意味と取得経路を明確にする

既存カタログを拡張し、各系列に次を対応づける。

- 何を確認する統計か、対象業種・企業KPIとの関係。
- 統計作成機関、配信元、元の系列・分類コード、取得URL。
- 国・地域、業種・品目、頻度、単位、基準年、季節調整、名目・実質。
- 必要履歴、公表予定、保存先、アプリへの供給先、利用条件。
- 実装・取得・保存・表示・継続更新の到達状況と、未達理由。

全国総合と業種別、PMIと景気先行指数、金額と数量、原指数と季節調整値は別系列として扱う。代理指標を、本来必要な統計の取得済み件数に含めない。

### 原本と改定前後を残す

取得した公式応答・ファイルを、取得時刻・内容のハッシュ・取得条件と結び付けて保全する。認証情報は保存対象から除く。

同じ月の数値・注記・速報区分が変わった場合にも、新しい版として保持する。全国IIPの「最新月と件数が同じ訂正で旧値を失う問題」と、業種別IIPの原応答保全を先に修正する。

「最新版の長期履歴」と「当時公表されていた値」は分ける。公表日時が不明な場合は不明のまま保持し、取得日時や観測月から作らない。Eurostatは原則として最新版のみを提供するため、自前の取得履歴が必要になる。［Eurostatの仕様］(https://ec.europa.eu/eurostat/web/user-guides/data-browser/api-data-access/api-introduction)

### 欠損と遅延を原因別に扱う

次の状態を既存の監視・再取得機構で区別する。

- まだ公表されていない。
- 発表元にはあるが、配信元への反映が遅れている。
- 通信・認証・利用上限で取得できない。
- 表ID・分類・ファイル形式が変わり、解釈できない。
- 取得できたが、欠損・単位・定義の検証に合格しない。
- 保存できたが、アプリへ届いていない。
- 元から提供されていない、または利用条件が未確認。

鮮度は、処理の成功時刻だけで判定しない。**公式に利用可能な最新期間と保存期間の差**を確認する。公表予定が確認できる系列は、原則として公表後の翌営業日までに追随することを運用目標とする。

再取得は既存キューを使い、欠けた系列・期間に限定する。途中失敗後に再開でき、同じ入力の再実行で重複しない形にする。品質不一致時は対象単位の公開を止め、最後に確認済みの値とその古さを残す。

### 既存のアプリ経路を使う

統計一覧・系列詳細の既存APIを継続利用する。値と併せて出典、期間、改定状態、欠損理由、鮮度を伝え、不足する情報だけ互換性を保って追加する。

取得器、保存、API、通常アプリの表示を一続きで検証する。共通SDMX対応は、採用する系列と提供元が具体化した段階で必要な部分を共通化する。

## 4. 実施段階と各段階の成果

| 段階 | 実施内容 | 次へ進む条件 |
|---|---|---|
| 0：現状と不足の確定 | 日米の必要項目、33業種の対応、保存期間、公式最新期間、アプリ供給先を照合。既存復旧作業の成果と未完を取り込む | 各項目に「取得済み／要修正／要追加／未提供／未確認」の根拠がある |
| 1：既存データの正確性を修正 | IIPの改定保全・業種別更新、機械受注等の履歴、系列定義、公表日時、鮮度判定を修正 | 同月訂正、欠損、定義変更を検出でき、公式値と保存値の照合が通る |
| 2：日米の共通統計を充足 | 既存取得器の設定追加・修正を優先し、必要な場合に公式API・ファイル経路を追加。最新期間を先に確保し、履歴を分割補完 | 合意した必要項目について最新値・必要履歴・出典・欠損理由が揃う |
| 3：産業と海外を拡張 | 半導体・機械・自動車から、品目別貿易、台湾・韓国、米中欧の関連産業を追加 | 各追加系列に用途・対象範囲・利用条件・既存系列との差が説明されている |
| 4：継続運用とアプリを確認 | 定期実行、再取得、監視、既存画面への供給を確認 | 定期処理の成功に加え、実際の次回公表・改定への追随と通常アプリの表示を確認できる |

段階1〜3では、各まとまりが検証を終えた時点で利用可能にし、全33業種の完成を待たせない。

IIP・機械受注、財務・開示の既存復旧作業は担当範囲を維持する。財務側の復旧記録にはDB整合性の問題もあるため、共通保存基盤に影響するかを確認してから大量履歴取得へ進む。今回、財務側の最新DB状態までは再検証していない。

## 5. 検証・完了条件と文書化

### 正確性を確かめる検証

既存の関連テストを拡張し、次を確認する。

1. **意味の一致**：期間、単位、基準年、季節調整、分類が公式定義と一致する。
2. **値の一致**：同じ定義・同じ版で公式値と照合する。異なる改定版の差は理由を記録する。
3. **改定の保存**：最新月・件数が変わらない訂正でも、改定前後を再現できる。
4. **欠損の検出**：系列・期間・ページの不足を検出し、ゼロや正常値に置き換えない。
5. **再実行の安全性**：重複、途中中断、通信制限からの再開で、欠落や二重反映が起きない。
6. **時点の正しさ**：公表前の値を当時利用可能だったものとして返さない。不明は不明とする。
7. **実際の供給**：公式資料→保存→API→通常アプリで、値・出典・期間・品質表示が一致する。

### 網羅性の測り方

API数や取得行数を網羅率には使わない。必要項目を分母として、次を別々に集計する。

- 必要な系列が取得できている割合。
- 必要な観測期間が揃っている割合。
- 公式最新期間へ追随している割合。
- 出典・定義・改定情報を確認できる割合。
- アプリで参照できる割合。

無料では取得できない項目、公式に存在しない項目、利用条件が未確定の項目も不足一覧に残す。分母から黙って外さない。

月次統計は、定期ジョブが成功した段階を「運用接続済み」、次の実公表に追随できた段階を「公表追随確認済み」として区別する。

### 計画書として残す内容

文書化時は、日本語Markdownの「統計データ収集基盤計画」を作成し、本計画の目的・現状・収集範囲・実施段階・受入条件をまとめる。既存の情報ソース拡張計画とは、今回の対象部分の役割を整理して相互に案内する。

系列ごとの大量の定義は既存カタログを正本とし、計画書には用途と優先順位を記載する。実測結果は確認日付きの証拠、進捗は既存の次アクション管理台帳で管理する。

本案は調査・計画の成果であり、コード、DB、定期実行、アプリへの変更はまだ実施していない。

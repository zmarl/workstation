**授権の範囲を推測で広げない。1 文聞けば済む。**

**Why**: 2026-08-31、オーナーに「投資判断の中核 80 機能が停止しているのを知っていたか」と尋ね、
「知っていた。このままで良い」と回答を得た。**そこから「では停止から漏れていた 2 本にも
同じ停止を適用してよい」と読み替えた**が、これは**80 本を止めたままにするかへの答え**であって、
**稼働中タスクを止めてよいかへの答えではなかった**。しかも**その 30 分前に自分で
「稼働中タスクの停止は運用変更でユーザー未依頼だから実行しない」と結論していた**。
並行セッションの指摘で聞き直したところ、回答は **「後で決める。今は保留」** ——**推測は外れていた**。

**技術的な誤診は DB を叩けば決着するが、授権の範囲には叩ける対象が無い。**
唯一の検証手段が「本人に聞く」ことしかない点で、他のあらゆる不確実性と性質が違う。
しかも**根拠を並べれば並べるほど正当に見える**ので、自分では気づけない。

**How to apply**:
- **稼働状態を変える操作**（タスクの停止・再開、スケジュール変更、設定の変更）は、
  包括的な許可があっても**その操作について**の許可かを確認する
- 判断の前に「この回答は**何への**答えだったか」を一度言い直す。
  「80 本を止めたままにする」と「2 本を新たに止める」は別の問いだった
- **聞くコストはほぼゼロ**。上記は 1 問 1 答で済み、しかも
  **どちらに転んでも情報が増える**（推測が当たっていれば推測の妥当性が実測される）
- 対照的に、**調査・診断は包括許可の範囲内**として進めてよい。
  2026-08-31 に「データ欠損があれば取得体制を整えて取得しておいて」の下で
  e-Stat API を read-only で叩いた判断は、稼働状態を変えないので性質が違う

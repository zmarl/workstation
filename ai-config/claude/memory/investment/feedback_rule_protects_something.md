機構・検査・契約に阻まれたとき、**外す提案をする前に、それが何を守っているかを特定する**。
2026-08-31 に 3 回ぶつかり、**3 回とも規則の側が正しかった**。

| 対象 | 「不要」と読んだ根拠（すべて事実として正しい） | 実際に守っていたもの |
|---|---|---|
| `require_creation_source` | 戻り値が使われない／worktree は `origin/main` か明示 SHA から作るので作業ツリーに非依存 | **AGENTS.md「main checkout では編集しない」を機械的に検知する唯一の経路**。当日それが実際に違反を捕まえた |
| `validated_attempts` の `synthetic ... cannot bind a log` | 診断を載せたいだけなのに双方向強制が邪魔 | **ログ＝プロセスが走った証拠**。走っていない合成 attempt に付けると「テストレーンが動いた」と誤読させる |
| `_escape_percent` の `%s` 免除 | リテラル内外を区別できない欠陥に見える | **`%s` は本物のプレースホルダ構文**。免除しなければ何も動かない。欠陥は免除ではなく区別できない点だけ |

**Why:** 「不要」を導く観測（戻り値未使用・土台は引数で決まる・免除が区別できない）は**どれも正しいのに、
結論だけが誤る**。検査は**値を返すためではなく、拒否するために在る**ことがある。自己検証では捕まらず、
根拠を並べるほど正当に見える点で [[feedback-authorization-scope-inference]] と同じ性質を持つ。
外していたら、**守られていたものが静かに消え、それに気づく経路も同時に消えていた**。

**How to apply:** まず **その規則を名指ししているテストを読む**（`test_..._allows_only_...` の
「拒否される側」の変数名が意図を語る。`"peer edit"` が決定打だった）。次に **AGENTS.md / ODR に
対応する規約があるか**を確認する。そのうえで、**規則を緩めず経路を変える**解を探す
（診断を別チャネルへ、SQL 側を直す、など）。上の 3 例はすべてこの形で解決した。
**ODR-0018 の「足さない」は「守っているものを外してよい」ではない。**

なお同型として、**同じファミリーの欠陥は同じ PR で全数潰す**（12 箇所のうち 1 箇所だけ直すと
「次に落ちた場所」で同じ状態に戻る）。
